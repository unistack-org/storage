# GC, arenas и размещение в CRUSH-движке

Мандат: размещение (вызов CRUSH `do_rule`) находится на горячем пути каждого
объекта. Go-GC не должен влиять на хвостовые задержки, а аллокации — расти
пропорционально числу запросов.

## Задача

Один вызов `DoRule` на кластер 225 OSD (3-tier, straw2, chooseleaf 3x)
использует временные буферы:

| Буфер                              | Размер             |
|------------------------------------|--------------------|
| `out []int` (результат)            | ≤ 100 int          |
| `a/b/c []int32` (кандидаты choose) | 3 × 128 int32      |
| `perm` в WorkBucket (кэш перестановок) | по размеру бакета, 1 раз на бакет |

История эволюции:

1. **`make()` на каждый вызов** — 7 аллокаций, 5.7 KiB на размещение
   (замер `BenchmarkMakeCarve`: ~700 ns/op, 5712 B/op, 7 allocs/op).
   Для Vitastor-класса IOPS (сотни тысяч размещений/сек на ядро) это
   генерировало гигабайты мусора в секунду → GC-шитспайки в tail-задержках.
2. **`unsafe` + GC-барьеры** (первая версия): слайсеры указателей в
   кастомной памяти. Опасно: GC не видит записи указателей в не-Go памяти,
   теряются объекты; write-барьеры приходится вставлять вручную
   (`runtime.gcWriteBarrier`). Отказались: хрупкость не окупается.
3. **Arena поверх `syscall.Mmap`** — финальное решение (см. ниже).

## Что даёт mmap-арена

Реализация: [`crush/arena.go`](../crush/arena.go) (+ `arena_unix.go`,
`arena_other.go`).

* **Нулевые аллокации в горячем пути.** `NewWork(m, resultMax, arena)`
  один раз отрезает от арены `a/b/c` и `perm`-массивы; `DoRule`
  переиспользует их на каждое размещение. Замер `BenchmarkDoRule`
  (225 OSD, 3-tier straw2, rep 3):

  ```
  BenchmarkDoRule-8   200000   ~34500 ns/op   0 B/op   0 allocs/op
  ```

  **0 B/op, 0 allocs/op** — GC не видит ни одной единицы работы на
  размещение, GC-трейс не сканирует рабочие буферы.
* **GC-невидимость.** Страницы `mmap(MAP_ANON)` не принадлежат куче Go:
  у них нет `mspan`, GC их не сканирует и не учитывает в goal-эвристике
  (`GOGC` не раздувается из-за рабочих буферов).
* **Скорость нарезки:** ~290 ns за нарезку 7 буферов против ~700 ns у
  `make()` — в ~2.4 раза быстрее, и без записи в GC-метаданные спана.
* **Предсказуемая память.** Арена = ровно `mapped` байт на воркер
  (64 KiB по умолчанию, блоки кратно странице). На N воркеров размещение
  занимает N × 64 KiB RSS и никогда не растёт без явной команды.

## Ограничение: только скалярные данные

Правило: **в арене живут только `int32/uint32/float` буферы. Память с
указателями — исключительно на куче Go.**

Причина: GC сканирует кучу по метаданным спана. Для `mmap`-памяти метаданных
нет, поэтому указатель, записанный в такую память, становится невидимым для
GC → сборщик может собрать объект, на который он указывает (floating pointer
→ крэш/порча данных). Поэтому массив `WorkBucket` (содержит слайсеры
`permX/permN` → указатели) выделяется обычным `make`, а из арены берутся
только целочисленные `perm`-массивы. Это компромисс «безопасно по
конструкции» вместо ручной игры с `runtime.gcWriteBarrier`.

## Сравнение альтернатив

| Подход | Плюсы | Минусы |
|---|---|---|
| `make()` per call | просто | 7 allocs, GC-шитспайки, гигабайты/с мусора на ядро |
| `sync.Pool` | переиспользование | GC-видим (сканирует слоты), boxing в `Get/Put`, очищается на каждом GC (амортизация пропадает в простое) |
| `unsafe` + ручные барьеры | максимум контроля | легко получить висячие указатели; поддержка дороже скорости |
| `GOEXPERIMENT=arenas` (Go 1.22+, у нас 1.27) | официальные арены, «allocate and forget» | **экспериментальный флаг**; арена не конкурентно-безопасна; `FinalizeArena` обязателен для больших арен; флаг меняет сборку всего бинарника — неприемлемо для библиотеки |
| **mmap-арена (наше решение)** | 0 allocs, GC-невидимость, нулевые зависимости, стабильно без флагов | только скаляры; ручное управление жизненным циклом (один владелец-воркер) |

Вывод: домен CRUSH идеально ложится на mmap-арену — рабочие данные это
массивы `int32` (item ids, веса, перестановки), указателей в горячем пути
нет. `GOEXPERIMENT=arenas` можно перепроверить при стабилизации API;
наш интерфейс `NewWork(m, resultMax, arena)` уже совпадает по смыслу с
`arenas.New[T](max)`, миграция будет тривиальной.

## Модель конкурентности

Арена **не** конкурентно-безопасна (bump-курсор). Правильная модель для
unistack: **один `Work` + одна арена на воркер-горутина** (per-shard),
`Map` — read-only после компиляции. Это же требование у Vitastor
(per-OSD размещение) и у Ceph CRUSH (`crush_work` per mapper).

`Work.Free()` освобождает только приватную арену (созданную при
`arena == nil`); арена, переданная извне, живёт дольше `Work` — владелец
освобождает её сам и обязан не делать `Reset` во время использования.

## Дальнейшая оптимизация (дорожная карта)

* Кэш `pg → osd[]` (как `pg_mapping` у Vitastor): размещение CRUSH один раз
  при создании/реплейсе PG, дальше O(1) lookup. При 0 allocs и ~34 µs на
  сложное трёхуровневое размещение даже без кэша это снимает CRUSH с пути
  клиентских I/O полностью.
* Bucket-permute кэш уже в `WorkBucket` — перестановки straw2/straw
  считаются один раз на бакет на воркер (амортизированно O(1)).
* Бинарный поиск в `bucket_list` (sum_weights упорядочены) — кандидат при
  появлении list-бакетов в профиле; в Ceph list практически не
  используется, приоритет низкий.
