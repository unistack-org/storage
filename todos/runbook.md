# Runbook полигона (2 ноды × 2 NVMe)

Статус на сегодня: снапшоты, клоны и откат (M3) — работают;
background-recovery — работает. Ниже — рабочие операции и поведение при
отказе ноды. Схема полигона и арифметика репликации: `test-vm-plan.md`,
раздел M6.1.

## Запуск

Каждая нода: 2 OSD (по одному на NVMe), meta поверх raft, admin API.

```
# нода A (10.0.0.1) и нода B (10.0.0.2), третья нода-свидетель (10.0.0.3):
# (в простой одно-сетевой конфигурации вместо -osd id@dir@addr достаточно
#  -data-dir /mnt/nvme1/osd0: id назначаем автоматически, адрес 127.0.0.1)
unistord -meta-dir /var/lib/unistord/meta \
  -osd 0@/mnt/nvme1/osd0@10.0.0.1:7000 -osd 1@/mnt/nvme2/osd1@10.0.0.1:7001 \
  -crushmap /etc/unistord/crush.map \
  -replicas 2 -min-size 1 -pg-num 64 \
  -raft 10.0.0.1:9401 -raft-peers 10.0.0.1:9401,10.0.0.2:9401,10.0.0.3:9401 \
  -raft-proxy 10.0.0.1:9501 -raft-proxy-peers 10.0.0.1:9501,10.0.0.2:9501,10.0.0.3:9501 \
  -http 0.0.0.0:8443 -metrics 0.0.0.0:8080 -vacuum-interval 300
```

Третья нода — свидетель без дисков: тот же `-raft`, без `-osd`.
Она даёт кворум meta (2 из 3) и поэтому кластер **переживает смерть
любой из двух storage-нод**: контроль пишет, вторая нода обслуживает I/O.
Без свидетеля (2 voters) потеря ноды = meta только на чтение.

Вместо `-osd id@dir@addr` можно использовать `-data-dir /mnt/nvme1/osd0`
(id назначается автоматически). На полигоне с несколькими дисками
рекомендуется смонтировать разделы по `UUID=` и передавать
`-data-dir uuid=<идентичность>@<путь>` — подробности в разделе
«Перепутанные диски» ниже.

## Перепутанные диски: защита и действия оператора

Смонтированные по именам ядра (`/dev/sdb`) разделы после перезагрузки
могут сменить имена: два диска меняются mount-точками местами, и OSD
без проверки начинает отдавать чужие данные под своими id. Демон этого
не допустит: id каждого `-data-dir` привязан к устройству.

Устройство опознаётся по стабильной идентичности (UUID ФС → serial →
WWID). Она печатается в:

```
unistorctl disk probe /mnt/nvme1/osd0
```

(там же UUID ФС для fstab и предупреждение, если fstab ссылается на
диск по имени ядра). Демон закрепляет идентичность в `<dir>/device` и
`<meta-dir>/devices.json`, пишет её в регистрацию OSD в мете
(`unistorctl osd ls`, колонка DEVICE) и при каждом старте сверяет с
живой. Несовпадение — fatal; что делать:

1. `disk probe` обоих каталогов — какая идентичность живёт где сейчас;
2. если диски реально поменялись mount-точками (fstab по `/dev/sdX`) —
   починить fstab на `UUID=<uuid из probe>` и перемонтировать корректно;
3. если переезд осознанный (диск переставили на другой mount),
   зафиксировать это явно: `-data-dir uuid=<идентичность>@<новый путь>`.

Явная форма `uuid=...@...` снимает и вторую неоднозначность: два
каталога на диске A и два на диске B без закреплённых идентичностей —
демон не угадывает соответствие, а требует uuid=. Несколько каталогов
на одном диске легальны — каждый каталог сохраняет свой id.

Проверка кластерная: OSD с id, зарегистрированным на другом устройстве,
не стартует даже на «правильном» узле — это ловит и ручные
`unistorctl osd add` с чужим диском.

## Проверить здоровье

```
unistorctl status -http http://10.0.0.1:8443
curl -s http://10.0.0.1:8443/v1/status | jq
```

Показывает: OSD live/evicted (пинг), вес, epoch карты, здоровье томов
(live targets vs min_size), место на локальных дисках, список warnings;
`healthy: true` — всё в норме. Опрос `/v1/status` раз в 10–15 с — готовая
замена алертам до появления `/metrics`.

## Метрики (VictoriaMetrics / Prometheus)

`-metrics 0.0.0.0:8080` поднимает отдельный экспортёр
`http://0.0.0.0:8080/metrics` (текстовый формат Prometheus — его
скрейпит VictoriaMetrics нативно). Единственный путь метрик —
`go.unistack.org/micro-meter-victoriametrics/v5` (реестр `metrics`
официальной библиотеки VictoriaMetrics, Prometheus-compat режим для
гистограмм `*_bucket{le=...}`); `prometheus/client_golang` в демоне
нет. Метрики живут ТОЛЬКО на этом
отдельном порту — админ REST API (`-http`) их не отдаёт; флаги
полностью независимы.

Используется опубликованный `v5.0.2` (берётся из прокси, без вендоринга).
Предшествующий тег `v5.0.0` было нельзя импортировать: go.mod требовал
`micro/v5 v4.1.25` и `micro-proto/v5 v4.1.0` (невалидный semver для
путей `/v5`) и подменял `VictoriaMetrics/metrics` форком. Починка
замержена в upstream (PR #182, ветка `v5`) как `v5.0.1`: реальные
v5-версии зависимостей, тест плагина починен под удалённый из micro/v5
`codec.Frame`. В `v5.0.2` (PR #183) восстановлен replace производительного
форка `github.com/VictoriaMetrics/metrics => github.com/NickPak/metrics v1.43.1-perf`.
Важно: replace библиотеки не наследуются потребителями — storage/go.mod
несёт его явно; проверка: `go list -m github.com/VictoriaMetrics/metrics`
должен показывать `=> github.com/NickPak/metrics v1.43.1-perf`.

Семейства (префикс `unistor_`):
- кластер: `unistor_cluster{name=osds|osds_live|healthy|volumes|
  map_epoch|raft_has_leader}`, ёмкость `unistor_cluster{name=
  total_raw_bytes|free_raw_bytes|used_raw_bytes}` (сумма по OSD,
  ответившим на StatFS);
- raft: `unistor_raft_state{state}` (leader/candidate/follower),
  `unistor_raft_member{id,addr}` (1=важированный участник, 2=лидер);
- OSD: `unistor_osd{osd,addr,name=up|weight}`,
  `unistor_osd_disk_bytes{osd,name=stored|free|total}` — побайтно по
  ВСЕМ OSD кластера (Sonar-зонд + StatFS по протоколу; свои OSD
  дополняются локальной статистикой),
  `unistor_osd_pool_connections{osd,state}`, `unistor_osd_connections{osd}`;
- скорость: счётчики `unistor_osd_requests_total{osd,op,status}`,
  `unistor_osd_bytes_total{osd,op,direction}`, гистограмма
  `unistor_osd_request_duration_seconds{osd,op}` (аналогично по экспортам
  `unistor_export_*` + QoS `unistor_export_qos_limit|qos_sustained`);
- тома: `unistor_volume{name,metric=writable|degraded|live_targets|...}`,
  состояние PG `unistor_volume{name,metric=pgs|pgs_ok|pgs_degraded|
  pgs_down}` (аналог vitastor_pg_count), ёмкость
  `unistor_volume{name,metric=size_bytes|used_bytes|raw_to_usable_bytes|
  space_efficiency}` (space_efficiency = отношение полезного объёма
  к сырому, сейчас 1/replicas);
- восстановление: `unistor_recovery_copies_total`,
  `unistor_recovery_bytes_total` (счётчики сработавших прогонов
  recovery на этой ноде);
- автовакуум (аналог postgres «age до autovacuum»): `unistor_vacuum{name=
  tombstones|objects|bytes|oldest_seconds|interval_seconds}` — очередь
  мусора удалённых томов из meta-БД: сколько записей/объектов/байт
  ждёт unlink и насколько оно старое (`oldest_seconds` против
  `interval_seconds` = сколько автовакуум ещё не добирал).
  `bytes` — сколько места на дисках освободит вакуум; алерт:
  `oldest_seconds > 3*interval_seconds` — автовакуум отстаёт;
- перезагрузка (см. §TLS): `unistor_reload{name=enabled|declarative|
  reloads|last_ok|last_reload_timestamp|last_error}` — `reloads`
  (счётчик всех попыток), `last_ok` (1/0 — итог последней),
  `last_reload_timestamp` (unix-время), `last_error` (1, если у
  последней были упавшие секции), `declarative` (1 — секции
  qos/crushmap/volumes участвуют, то есть демон с `-meta-dir`). Алерт:
  `unistor_reload{name="last_ok"} == 0`;
- TLS (см. §TLS): `unistor_tls{name=enabled|expiry_seconds|
  not_after_timestamp|reloads|last_reload_timestamp|last_error|
  skip_verify|plane_data_enabled|plane_raft_enabled|plane_nbd_enabled|
  plane_admin_enabled}` — одно семейство на весь жизненный цикл сертификата. При выключенном TLS остаётся только `enabled=0`. Алерты:
  `unistor_tls{name="expiry_seconds"} < 86400*7` (истекает) и
  `unistor_tls{name="last_error"} == 1` (последняя перезагрузка материала
  упала — демон живёт на старом).

Средние считайте через `rate()` / `histogram_quantile()` — все величины
усреднённые, не «сумма средних».

Конфиг скрейпа (на каждую ноду):

```yaml
scrape_configs:
  - job_name: unistord
    static_configs:
      - targets: ["10.0.0.1:8080", "10.0.0.2:8080", "10.0.0.3:8080"]
```

Алерт-заготовка: `unistor_cluster{name="healthy"} == 0` (5 мин),
`unistor_cluster{name="osds_live"} < unistor_cluster{name="osds"}`.

## Диск ВМ: создать, залить образ, выдать гостю

```
unistorctl vol create vm-042 40G -quota 20G -replicas 2 -min-size 1
qemu-img convert -f qcow2 -O raw disk.qcow2 disk.raw
curl -T disk.raw 'http://10.0.0.1:8443/v1/volumes/vm-042/import'
# либо демон сам скачает: curl -X POST .../import -d '{"url":"http://files/disk.raw"}'
# и с проверкой по файлу контрольных сумм (демон сам скачает и сверит хеш):
#curl -X POST .../import -d '{"url":"http://files/disk.raw","sha256_url":"http://files/SHA256SUMS"}'
# алгоритмы: md5 / sha256 / sha512, у каждого своё поле и поле *_url:
# curl -X POST .../import -d '{"url":"http://files/disk.raw","md5_url":"http://files/MD5SUMS"}'
unistorctl export create vm-042 -type vduse -devname sds-vm042   # гость видит sds-vm042
```

Импорт возможен только в уже существующий том (404, если его нет):
«импортировать в никуда» нельзя. Ровно один дайджест на импорт:
шесть полей (md5, md5_url, sha256, sha256_url, sha512, sha512_url) —
взаимно исключающиеся, два и больше ⇒ 400. Файл сумм читается тем же
SSRF-защищённым клиентом, что и образ, и расшифровывается до первого
байта записи — не смог скачать/разобрать сумму ⇒ 502, том остаётся
нетронутым. Формат файла: голый хеш, `algo:<hex>`, `hash  имя`
(md5sum/sha256sum/sha512sum, есть и бинарный `hash *имя`),
`ALGO(имя)= hash`, а также листинг из нескольких строк — строка
берётся по имени файла образа. Дайджест из файла принимается только
если его длина соответствует запрошенному алгоритму (md5-файл не
заменит sha256-проверку).

Квота 20G на томе 40G = тонкий том: гость упрётся в ENOSPC раньше, чем
кончится реальное место. Полное удаление раздела/TRIM освобождает место.

## Снапшоты и откат

Снапшот не двигает данные: том «замораживается» в поколение, новая запись
идёт в свежий диапазон OID, чтение идёт по цепочке поколений (новое →
старое). Секундная операция на любом размере тома. Откатывает том в
снапшот и выбрасывает всё, что было написано после него.

```
unistorctl vol snap create vm-042      # -> snapshot 1 (...)
unistorctl vol snap ls vm-042          # поколение, дата, размер, объекты
unistorctl vol snap rollback vm-042 1  # том = снимок, снапшот 1 израсходован
unistorctl vol snap rm vm-042 1        # удалить снапшот (освободить место)
```

То же по HTTP (админ-адрес):

```
curl -X POST http://10.0.0.1:8443/v1/volumes/vm-042/snapshot      # 201 + gen
curl       http://10.0.0.1:8443/v1/volumes/vm-042/snapshots
curl -X POST -d '{"gen":1}' http://10.0.0.1:8443/v1/volumes/vm-042/rollback
curl -X DELETE http://10.0.0.1:8443/v1/volumes/vm-042/snapshot/1
```

Что нужно помнить:

- **Откат необратим**: данные после снапшота выбрасываются (их поколения
  уходят в вакуум), сам снапшот при этом расходуется (его данные становятся
  живым томом). Если текущее состояние жалко — сделайте снапшот перед откатом.
- **До 64 снапшотов на том** — это глубина цепочки чтения; дальше — ошибка.
- **Trim внутри снапшота материализуется**: после снимка запись нуля пишет
  настоящие нули (дырку прошить нельзя — снапшот её потерял бы).
- **Resize тома со снапшотами запрещён** (геометрия поколений фиксирована).
- Место, занятое снапшотами, видно в `vol snap ls` (сумма объектов
  поколений); `vol info` показывает usage живого тома без снапшотов.
- Удалённый снапшот вычищается с дисков сразу (тот же вакуум-движок,
  идемпотентный); при недоступной ноде — на следующем проходе.

Типовой сценарий полигона: снапшот перед прогоном тестов → сломали ВМ →
`vol snap rollback` → та же чистая машина за секунды.

## Клонирование томов (партии одинаковых ВМ)

Клон — это копия меты: у клона свой свежий диапазон OID, а читает он
базовый образ по расшаренной цепочке снапшотов источника (источник
предварительно флешится и замораживается ещё одним поколением). Ноль
копий данных: клон 64 GiB — несколько записей в мету, секунды.

```
unistorctl vol clone base vm-042              # квота наследуется от base
unistorctl vol clone base vm-043 -quota 10G   # своя квота
```

```
curl -X POST -d '{"name":"vm-042"}' http://10.0.0.1:8443/v1/volumes/base/clone
curl -X POST -d '{"name":"vm-043","quota":10737418240}' http://10.0.0.1:8443/v1/volumes/base/clone
```

Ответ 201 + карточка клона; 404 — нет источника; 409 — имя занято или
цепочка источника на лимите (64).

Что нужно помнить:

- **Клон — обычный том**: пишется, снапшотится, откатывается,
  экспортируется, удаляется; QoS и геометрия наследуются от источника
  (клон принимает только квоту — раскладка цепочки обязана совпадать).
- **CoW**: запись клона идёт в его собственный диапазон — источник
  ничего не видит. Первый read промазывает в живой диапазон и читает
  через цепочку.
- **Удаление источника безопасно для клона**: ссылки на расшаренные
  поколения считаются (genrefs); вакуум источника вычищает только его
  личные диапазоны. Клон удаляется последним — тогда объекты уходят.
- **Квота считается по живым блокам клона** консервативно: расшаренные байты
  источника в usage клона не входят, но первая запись блока заряжает
  1× размер блока.
- `vol snap create` источника после клона — обычная операция: источник
  остаётся владельцем своей цепочки, клон несёт свою копию ссылок.

Типовой сценарий: залитый `base` (импорт через HTTP) → N клонов
`vol clone` → каждая ВМ живёт своей жизнью → не нужны — `vol rm`
(вакуум подчистит, когда последний читатель уйдёт).

## QoS и квота на живом томе

```
unistorctl vol qos vm-042 -r 2000:200M -w 1000:100M   # гость; админ (HTTP) не ограничен
unistorctl vol quota vm-042 30G                       # поднять потолок, том открыт
curl -X PUT .../v1/volumes/vm-042/qos -d '{"read_iops":500}'
```

Открытые тома подхватывают изменения на лету (meta watch).

## Изменить размер тома (онлайн)

```
unistorctl vol resize vm-042 40G                      # только рост; у shrink нет поддержки
curl -X PUT .../v1/volumes/vm-042/resize -d '{"size":42949672960}'
```

Том растёт без рестарта: метаданные дописываютExtent-диапазон объектов
(базовый диапазон фиксируется, новые объекты — из аллокатора, коллизий с
соседними томами нет). Квоту resize НЕ поднимает — это отдельное
решение (`vol quota`).

Как размер доходит до гостя:
- **VDUSE** (`-vduse`): демон сам замечает рост, обновляет config space
  и шлёт гостю config-прерывание — `/dev/vdX` растётся на лету.
- **NBD** (`nbd-client` в госте): размер отдаётся на handshake каждого
  нового подключения; гостю нужен reconnect/rescan:
  `echo 1 > /sys/block/nbdX/size` (или перемонтировать с ext4: `resize2fs`).
- **Одтонный `-export` file**: файл образа можно растянуть снаружи
  (`truncate -s +10G disk.img`) — новый handshake отдаст новый размер.
- **Одтонный `-store`**: размера из `-export name=path:size` хватает на
  старте; online-увеличение — через API бэкенда (SetSize), CLI-команды
  пока нет.

FS внутри гостя расширяет админ: `resize2fs /dev/vdX` / `xfs_growfs`.

## Смерть ноды

- **Свидетель жив**: кворум meta есть, second нода читает и пишет
  (RF2, min_size=1: запись на оставшуюся реплику проходит). Гость на
  умершей ноде, естественно, падает. OSD вытесняется по `out_time`
  (вес 0), `status` покажет `evicted` и предупреждение.
- **Свидетеля нет / умерли обе storage-ноды**: meta read-only —
  HTTP-записи отвечают 503 с подсказкой лидера, данные доступны на
  чтение, гостевые записи встают на паузу (hard-семантика) до
  возвращения ноды.
- Восстановление ноды: `-osd` на тот же data-dir → OSD сам
  регистрируется; расходящиеся/пропавшие объекты чинит recovery (M6.3):
  `unistorctl recovery ls` (что лечить) и `unistorctl recovery run vm-042`
  (копия с живой реплики, темп по умолчанию 200 iops / 200M/s — гостям
  не мешает).

## Drain OSD: выведение из кластера

Плановое выведение OSD (обслуживание, замена диска, снос ноды) — одна
команда:

```
unistorctl osd drain <id>                 # out + rebalance + recovery до healthy
unistorctl osd drain <id> -rm             # то же + удалить из реестра в конце
unistorctl osd drain <id> -dry-run        # показать план, ничего не писать
unistorctl osd drain <id> -iops 100 -bps 100M -timeout 30m   # медленнее/дольше
```

Что делает `drain` по шагам:
1. `osd out <id>` — вес 0, OSD выпадает из placement (новые реплики на него
   не ставятся).
2. `rebalance` — пересчитывает веса живых OSD пропорционально свободному
   месту, чтобы освободившееся место распределилось равномерно.
3. Цикл recovery: `recovery ls` → пока есть расхождения, `recovery run`
   (копия с живой реплики, темп `-iops`/`-bps`, по умолчанию 200 iops /
   200M/s) → повторный скан. Остановка: всё healthy, либо `-timeout`
   (по умолчанию 10m), либо том не открывается (pseudo-отчёт — recovery
   его не починит, выход с ошибкой).
4. `-rm` — после healthy `osd rm <id>`: запись из реестра удалена.

Ручной вариант (если хочется контролировать каждый шаг):

```
unistorctl osd out <id>          # вес 0
unistorctl rebalance             # перераспределить
unistorctl recovery ls           # что осталось докопировать
unistorctl recovery run <том>    # до healthy (повторять по ls)
unistorctl osd rm <id>           # только когда weight 0 и всё healthy
```

`osd rm` отказывает, пока `weight != 0` — нельзя выкинуть из реестра OSD,
который ещё в placement: его реплики «потеряются» без переноса. Сначала
`osd out` / `osd drain`.

**Важно про `rm` и перезапуск.** OSD при старте сам перечитывает свою
запись из меты и обновляет её (сохраняя вес и UUID). Поэтому `osd rm`
смысленен только для **остановленного** (или уже выведенного и
остановленного) OSD: если демон с этим id снова запустится, он
перерегистрируется. Порядок сноса ноды: `osd drain <id> -rm` → остановить
демон → снести/заменить диск. Если нода возвращается — просто `-osd` на
тот же data-dir, OSD сам вернётся в реестр (см. «Смерть ноды»).

Связанные секции: «Смерть ноды» (аварийное выведение по `out_time`),
«Recovery: починка реплик» (ручной `recovery ls`/`run`).

## Надёжность записи (commit-режимы)

Флаг `-commit` у `unistord` (для OSD и для `-store` экспортов) — где
заканчивается гарантированная стойкость записи. Это же лечит и цену WA:
чем строже режим, тем больше fsync на запись.

| Режим | Что происходит | Когда брать |
|---|---|---|
| `none` (умолчание) | запись уходит в page cache; диск fsync'ается когда гость шлёт FLUSH/FUA (гостевой барьер) или когда зовут `Volume.Flush()` | обычный гость с wce/FLUSH: гость сам знает, где ему нужен барьер |
| `flush` | каждый write/punch делает fsync до ответа | максимальная стойкость без поддержки барьеров у гостя; медленно |
| `sync` | файл открыт `O_SYNC`: fsync делает ядро на каждом write | то же, что flush, чуть дешевле; на macOS деградирует до flush-семантики |
| `journal` | запись дописывается в WAL (`<datadir>/journal.log`), fsync журнала — это и есть подтверждение; в объекты журнал «разглаживает» фоновый applier | каждая подтверждённая запись на носителя, но быстро: последовательный append в журнал вместо случайных записей+fsync в 4МБ объекты |

Смысл `none`: барьер гостя (FLUSH в NBD, REQ_FLUSH в VDUSE, FUA в
записи) — это и есть запрос «дочитай это на диск», сервер отвечает
только после fsync. Машина с целой батареей на контроллере NVMe живёт
именно так. `flush` платит fsync за каждую 4К-запись — порядок цифр:
тысячи iops против десятков тысяч.

`-fsync-batch` (например `2ms`, работает в режиме `none`): несколько
FLUSH'ей, пришедших в одно окно, объединяются в один проход fsync по
всему диску. Порядок не ломается — проход стартует *после* того, как
запись вызвавшего FLUSH клиента ушла в файл, поэтому вернувшийся FLUSH
всегда покрывает свои данные. N FLUSH'ей в секунду превращаются примерно
в 1/batch проходов.

Пример: `-commit none -fsync-batch 2ms` — дефолт по скорости + сглаженные
всплески fsync. Для «дешёвых» ВМ без гарантий на диск: `-commit flush`
(медленно, но каждая подтверждённая запись на носители).

### Journal: как это устроено

`-commit journal` — компромисс между `flush` и `none`: подтверждение
записи стоит одного последовательного fsync в журнал, а не случайной
записи в объект.

- Подтверждение (ack) = запись дописана в `journal.log` и fsync'нута.
  После этого она переживёт любое отключение питания.
- Фоновый applier (тик 20 мс) переносит записи из журнала в объекты и
  усекает журнал, когда тот целиком разглажен. Объекты «отстают» от
  журнала — это норма.
- Чтение видит все подтверждённые записи сразу: незакрытые записи
  накладываются поверх файла объекта (read-your-writes).
- `Sync()` (гостевой FLUSH) дополнительно разглаживает журнал в объекты
  и усекает его: после успешного FLUSH сами объекты полны.
- `Remove` — чекпойнт: журнал сначала целиком разглаживается и усекается,
  потом файл удаляется. Удалённый объект не воскреснет из журнала.
- Обрыв питания: при старте журнал проигрывается (рваный хвост
  обрывается на последнем целостном записи — tolerates), объекты
  достраиваются. Порча середины журнала — магазин не открывается
  (`journal corrupt`), это чинится вручную.
- Полный диск: append в журнал даёт ENOSPC → та же цепочка StatusNoSpace,
  что и у объектов; журнал после этого «отравлен» (sticky) до рестарта.
- Оверлей журнала ограничен (8192 записи): сверх лимита писатели сами
  помогают разглаживать журнал (backpressure), журнал не обгонит объекты
  бесконечно.

Журнал живёт в DataDir OSD и входит в размер диска: следите за
`MinFreeBytes` — при заполнении объекта журнал тоже упрётся в ENOSPC.

## TLS (шифрование транспорта)

Один набор файлов на узел: `-tls-cert` + `-tls-key` (сертификат узла) и
`-tls-ca` (наш CA). Сертификат и ключ задаются только вместе; ни одного
— кластер работает открытым текстом. `-tls-min-version` — по умолчанию
`1.2`.

### Плоскости: TLS включается точечно, не «всем сразу»

`-tls-planes` (по умолчанию `data,raft,nbd,admin`) выбирает, какие
плоскости шифруются; остальные остаются открытыми:

| плоскость | что шифруется |
|---|---|
| `data` | данные OSD (`sdsnet`, порты 7000/7001): репликация, recovery, vacuum, клиентские конны |
| `raft` | транспорт raft (`-raft`, 9401) и прокси записей (`-raft-proxy`, 9501) |
| `nbd` | upgrade-шаг `START_TLS` при подключении экспорта |
| `admin` | admin HTTP (8443) — серверный сертификат |

Ключевой сценарий: **данные открытым текстом, контроль за TLS** —
`-tls-planes raft,admin` (витастор-стиль: тяжёлый I/O идёт без
шифрования, меты и управление за mTLS). Синонимы имён плоскостей:
`osd`/`client` → `data`, `meta` → `raft`, `export` → `nbd`, `http` →
`admin`.

Плоскость — свойство пары «кто принимает / кто дёргает»: узлы должны
быть настроены одинаково по каждой плоскости, иначе конна на этой
плоскости просто не поднимется (клиент говорит «plain», сервер ждёт
handshake). Поэтому включать TLS по флоту — это проход по всем узлам,
а не по одному.

Admin API с серверным сертификатом, но без обязаловки клиентского:
клиентский сертификат требуется, только если отдельно задан
`-tls-client-ca-file` (тогда admin требует полный mTLS, и
`curl --cacert` перестаёт работать).

### Сертификат

Должен включать в SAN все адреса, по которым в узел дёлаются (IP тоже;
пример для 10.0.0.1):

```
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 \
  -nodes -keyout ca.key -out ca.pem -days 3650 -subj "/CN=unistord-ca"
openssl req -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes \
  -keyout node-a.key -out node-a.csr -subj "/CN=10.0.0.1"
openssl x509 -req -in node-a.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -days 825 -extfile <(printf "subjectAltName=IP:10.0.0.1,DNS:localhost\nextendedKeyUsage=serverAuth,clientAuth") \
  -out node-a.crt
```

Запуск: `unistord ... -tls-cert node-a.crt -tls-key node-a.key -tls-ca ca.pem`.

Admin API с проверкой CA (без клиентского сертификата):

```
curl --cacert ca.pem https://10.0.0.1:8443/v1/status
unistorctl -tls-ca ca.pem status -http https://10.0.0.1:8443
```

`unistorctl` флаги: `-tls-ca` — доверять нашему CA (https к admin и
экспорт/импорт); `-tls-cert`/`-tls-key` дополнительно — клиентский
сертификат для плоскостей, где нужен mTLS (прямые конны к OSD у
`vacuum`/`recovery`). Без `-tls-ca` https-сервер с самоподписанным CA
не примет сертификат — это намеренно.

### `-tls-skip-verify`: шифровать, но не аутентифицировать

Флаг на `unistord` и на `unistorctl`: канал зашифрован, но сертификат
пира не проверяется вообще (клиентом — цепочка и адрес; сервер
принимает любой сертификат и принимает соединение **без** сертификата
клиента). Это инструмент развёртывания и отладки: кластер в таком
состоянии подменяем кем угодно в сети, поэтому демон кричит
предупреждением на старте, показывает его в `/v1/status` и в
`unistor_tls`. С `-tls-skip-verify` `-tls-ca` не обязателен.

### Горячая перезагрузка: SIGHUP и POST /v1/reload

Без рестарта демон перечитывает всё декларативное: сертификаты,
QoS-классы, crushmap, список томов для `-create` и `GOGC`. Одна точка
на все триггеры — `SIGHUP`, `POST /v1/reload` и `unistorctl reload`
идут по одному пути; секции независимы и keep-last-good: битый crushmap
не мешает перечитать сертификаты, упавшая секция не роняет кластер.

```
# 1. положить новые cert/key (или править файл -crushmap) на те же пути
systemctl kill -s HUP unistord           # 2. SIGHUP = перезагрузить всё
                                          # (systemd сам HUP не шлёт)

# то же через API (Authorization: Bearer, если задан -admin-token)
curl --cacert ca.pem -X POST https://10.0.0.1:8443/v1/reload
unistorctl reload -http https://10.0.0.1:8443 -token T   # тот же отчёт
curl --cacert ca.pem https://10.0.0.1:8443/v1/tls         # только TLS, подробно
unistorctl -tls-ca ca.pem status -http https://10.0.0.1:8443   # st.tls, st.reload
```

Отвечает всегда полным отчётом: секции идут в порядке
`tls, qos, crushmap, volumes, gogc`, каждая помечена `applied` с
`detail` либо пропущенной с причиной (пропуск — не ошибка; секция
никогда не исчезает из отчёта молча). Упавшая секция даёт `error`,
отчёт `ok:false`, HTTP 500 — и остальной кластер продолжает работать
на старом материале; предупреждение попадает в `warnings` у
`/v1/status` (то есть `healthcheck` становится нездоровым), а
`restart_required` перечисляет флаги, которые перезагрузка не примет.
Секция crushmap публикует карту (`latest+1`) только когда содержимое
файла отличается от последней опубликованной — повторный reload ничего
не переопубликовывает. Перед публикацией карта проходит тот же
структурный контроль, что `unistorctl map check`, и компиляцию на
живом реестре OSD (если реестр пуст — только структура: первый мап
публикуют именно так). Битая карта не попадает в meta: опубликованная
эпоха — это placement для всех osd и всех клиентов, а на старте её
отбивает placement-проверка, которой у перезагрузки нет.

Опция `-tls-reload-interval S` — поллинг mtime сертификатов раз в S
секунд для тех, кому неудобен сигнал (0 = выключен, дефолт); она
касается только материала TLS. `POST /v1/tls/reload` остаётся: это
узкий TLS-only вариант того же пути.

Ограничения: **CA перечитывается только на старте** — ротация CA требует
рестарта; `-tls-planes` сменить на ходу нельзя (это состав слушателей,
а не материал). Слушатели (`-http`, `-listen`, `-raft`, `-metrics`),
бэкенды/OSD (`-store`, `-osd`, `-data-dir`, ...), `-admin-token` —
тоже только рестарт; они перечислены в `restart_required` каждого
отчёта.

### Наблюдение

`GET /v1/tls` (за токеном, как и остальные /v1-эндпоинты) — живой
материал: Subject/Issuer/Serial/SAN, `not_before`/`not_after`,
`expiry_seconds`, `skip_verify`, включённые плоскости (`planes`),
отключённые (`plain_planes`), счётчики перезагрузок и `last_error`.
`POST /v1/tls/reload` — перечитать файлы (то же, что SIGHUP); при
битом материале отвечает 500 с причиной и продолжает работать на
старом. Сжатое состояние лежит в `/v1/status` (`st.tls`), а истёкший
(или истекающий в сутки) сертификат и упавшая перезагрузка — это
записи в `warnings`, то есть `healthcheck` становится нездоровым.
Метрики — `unistor_tls` (см. §Метрики).

### Наблюдение за перезагрузками

Отчёт последней перезагрузки живёт в `/v1/status` (`st.reload`:
`reloads`, `last_at`, `last_ok`, `last_error`) и в семействе
`unistor_reload{name=enabled|declarative|reloads|last_ok|
last_reload_timestamp|last_error}` (см.
§Метрики). Алерт: `unistor_reload{name="last_ok"} == 0` — последняя
перезагрузка упала, демон живёт на старом материале; состояние
обновляется и SIGHUP, и REST, поэтому алерт ловит оба пути.

### Что TLS не покрывает

NBD/VDUSE-экспорт (`nbd-client`, ядро) TLS не понимает: порт экспорта
(10809) остаётся открытым каналом к данным, его выдают только в
доверенной сети либо через stunnel/WireGuard поверх. `nbd` в
`-tls-planes` шифрует служебный шаг подключения к unistord, а не сам
поток блока.

## Разделение сетей: кластер/контроль отдельно от дата-плейна

OSD слушает два адреса: дата-плейн (данные I/O, recovery, replication)
и опциональный контрольный (пинги, StatFS, health-пробы клиентов,
probe-раунды метрик и `/v1/status`). Контрольные пробы идут на
контрольный адрес,
поэтому забитая дата-сеть не выглядит как мёртвые OSD: кластер не
эвиктит живые диски и не начинает ложное recovery.

Задаётся четвёртым сегментом в `-osd`
(`id@data-dir[@host:port[@ctrl-host:ctrl-port]]`), порт 0 разрешён:

```
-osd 0@/var/lib/unistor/osd0@10.0.0.11:7000@10.0.1.11:7100
```

`CtrlAddr` попадает в регистрацию OSD в мете (`ctrl_addr`); пустой —
контроль идёт по дата-адресу (обратная совместимость со старыми
записями и одиночными стендами). Оба слушателя обслуживает один
sdsnet.Server: протокол идентичен, различается только сетевой путь.
В `/v1/status` адрес виден как `osd_detail[].ctrl_addr`.

Данные (чтение/запись, vacuum, recovery, placement) всегда идут на
дата-адрес — развязка только для контроля. TLS действует на оба
слушателя.

## Вакуум: освободить место после удаления томов и внутри живых томов

`vol rm` помечает том удалённым (тумбстон в мете), его объекты на OSD
снимает отдельный проход вакуума:

```
unistorctl vacuum ls                        # что копится (тумбстоны)
unistorctl vacuum run                       # снять объекты всех тумбстонов
curl -X POST http://10.0.0.1:8443/v1/vacuum # то же через HTTP (GET = список)
```

Точечно по одному тому (имя работает для обоих случаев):

```
unistorctl vacuum run vm-042                        # том ещё жив → punch
unistorctl vacuum run vm-042                        # том удалён → только его тумбстон
curl -X POST http://10.0.0.1:8443/v1/vacuum/vm-042  # то же через HTTP
```

Ответ HTTP различает режимы: `mode:"tombstone"` (снятые объекты по OSD)
и `mode:"live"` — вакуум живого тома: проход по объектам тома, каждый
полностью нулевой объект «пробивается» наsparse (fstrim-эквивалент
снаружи диска: гость удалил файл → TRIM → нули → vacuum освобождает
блоки на всех репликах). Живой vacuum читает объекты и сравнивает с
нулями — запускать в тишине; повторный проход по пробитым объектам
ничего не делает (нулевая аллокация пропускается без чтения).

Фоновый вариант — демон сам: `unistord -meta-dir ... -vacuum-interval 300`
(интервал автовакуума в секундах, 0 = выключен; трогает тумбстоны, живые
томы не читает). Объекты удаляются идемпотентно, проход можно повторять;
место на NVMe освобождается сразу после `Sync` OSD. Объекты пробиваются
дырами: на Linux — FALLOC_FL_PUNCH_HOLE, на macOS/APFS — fcntl(F_PUNCHHOLE)
(файл тонкий, размер виден прежний, блоки возвращаются ФС); на прочих
платформах нулевые области затираются на месте.

## Recovery: починка реплик

```
unistorctl recovery ls                       # тома с расхождениями
unistorctl recovery check vm-042             # пообъектный отчёт (items/down)
unistorctl recovery run vm-042               # залить недостающее с живой реплики
unistorctl recovery run vm-042 -iops 50 -bps 50M   # медленнее
curl -X POST 'http://10.0.0.1:8443/v1/recovery/vm-042?iops=1000&bps=0'
```

Скан сравнивает CRUSH-таргеты каждого объекта с реальностью на OSD;
объект «расходится», если лежит не на всех живых таргетах. Мёртвый OSD
попадает в `down` и задач не порождает — сначала верните/выведите ноду
(`unistorctl osd out <id>` при решении эвиктить, или `osd drain <id>`
для полного выведения). Починка идёт админской
полосой, ограниченной `qos` по записи (по умолчанию 200 iops / 200M/s).

## Мало места
