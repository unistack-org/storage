# Бенч-стенд: Vitastor 3.2.3 vs наш стек (sdsd) — первый отчёт

Дата: 2025-11-08. Стенд: `unibench` (192.168.1.100, доступ `ssh unibench`
через jump `ssh unistack.org`). Fedora, 64 CPU, 125 GB RAM, 2× Intel P4510
в md RAID1 (~24 GB свободно). Sudo нет → kernel-NBD/VDUSE недоступны,
сравнение идёт по **нативным userspace-путям каждого стека** (см. методологию).

## Методология

- **Диск здоров**: 2× Intel P4510 в md RAID1 `[2/2] [UU]`, SMART/состояние
  `live`. Прямой fio (io_uring) по файлу 512M на idle-диске, прогретом
  25 с seqwrite: randwrite 4K qd32×4 = **230K IOPS**, randread 4K qd32×4 =
  **337K IOPS**; QD1: randwrite 11.9K IOPS (avg 76 µs), randread 139 IOPS
  (md read-ahead 128K убивает одиночное random-read — 32× амплификация).
  Реальный steady-state потолок random-записи устройства ~65K IOPS
  (виден ниже по device-амплификации обоих стеков).
- **Хост шумит**: sglang/ollama (LLM-inference, 2×GPU 94% CPU). На хосте
  редкие NVMe-командные столлы ровно по 30 с (= `nvme_core.io_timeout=30`)
  — они дали выбросы «до 30 с» в обоих стеках (выбросы ровно 30.0х с —
  подпись таймаута ядра, не приложения). Замеры raw-диска скачут в ~30 раз
  в зависимости от фонового LLM-трафика; все сравнительные прогоны стеков
  сделаны в одном окне.
- **Наш стек**: один процесс `sdsd`, 3 OSD в процессе, vol0 6G rep3
  min_size=2, pg=64, crushmap в crushkv-тексте; клиент `sdsbench`
  (pipelined NBD-протокол поверх TCP loopback, Go).
- **Vitastor 3.2.3**: 3 file-OSD (по 4G, simple-offsets), etcd 3.5, пулы
  `rep1` (1/1) и `rep3` (3/2, pg_minsize=2, failure_domain=osd); клиент —
  fio + `libfio_vitastor.so` (C++ клиент). Глобальный конфиг из их CI:
  `immediate_commit=none`, `client_enable_writeback=true` (без writeback
  rep3-запись проваливается до 3.4K IOPS qd32).
- fio 3.40 собран локально (io_uring). Все замеры 4K, direct=1, time_based 15s.

## Выводы

1. **Латентность QD1 — наша сильно лучше** (randread 89 µs против 537–1224,
   randwrite 231 µs против 459–612). Один запрос в полёте — наш профиль
   (виртуалка с одним потоком, OLTP): примерно 2–6× быстрее.
2. **randwrite при равном суммарном QD и равной надёжности — паритет**:
   наши rep3 22.1K ≈ Vitastor rep3 (writeback) 22.3K. Объяснение через
   device-амплификацию: наши 22.1K × 3 реплики = 66K device-записей/с;
   Vitastor rep1 64.6K × 1 = 65K; Vitastor rep3 (wb) 22.3K × 3 = 67K.
   Все три упираются в один и тот же реальный steady-state потолок
   устройства ~65K random-write IOPS. Один наш конвейерный коннектор
   масштабируется линейно по соединениям (4×qd32 = 4×5.5K).
3. **randread — была наша просадка: 3×** (41.6K против 128K при QD128).
   Сырой idle-диск отдаёт 337K IOPS (io_uring; прежде фиксировались
   раздутые 1.09M из read-кэша) — узкое место не диск, а путь чтения:
   Go-клиент sdsbench (GC, один коннектор на процесс) + наша обработка
   READ в sdsd (по коннектору ~10.4K ops/s). **Исправлено 2025-11-08,
   см. секцию «Фикс чтения» ниже: 171–177K IOPS, Vitastor (129K) обогнан.**
4. **Налог репликации у Vitastor виден**: rep1 randwrite qd128 = 64.6K
   против 22.3K у rep3 (2.9×). Сравнивать «в лоб» rep1 с нашими rep3
   некорректно — мы держим паритет на равной схеме 3/2.
5. **Без writeback у Vitastor rep3 деградировал до 3.4K IOPS** (qd32×1,
   avg 9.4 ms): их дефолт для file-OSD непригоден, нужен глобальный конфиг
   `client_enable_writeback` — скрытая операционная зависимость.

## Операционные наблюдения (деплой Vitastor)

- Пул **не активируется без монитора**: нужен `vitastor-mon` (Node.js) +
  бинарник `lp_solve` (LP-оптимизатор размещения PG). Без них пул висит
  `inactive 0->64`. То есть полный стек = etcd + mon (node) + lp_solve +
  OSD; наш = один Go-бинарник.
- `failure_domain` по умолчанию `host`: три file-OSD на одном хосте
  размещаются не были вообще (пул inactive) — нужен `--failure_domain osd`.
- mon при записи pg/config для 64 PG rep3 упирался в `max-txn-ops` etcd
  (дефолт 128) → требовался etcd с `--max-txn-ops 10000` (у них в коде
  стоит FIXME про это).
- CLI-эвристики: `vitastor-cli create -p rep1 -i img1` парсит `-i` как
  размер и создаёт образ с именем `-pool`; все вызовы CLI в скриптах
  требуют `</dev/null`, иначе висят на stdin.

## Фикс чтения (2025-11-08): конвейер NBD-сервера

Причина просадки: transmission-цикл sdsd обрабатывал запросы строго
последовательно (потолок ~10.4K ops/s на коннектор). NBD-спека разрешает
переупорядоченные ответы при согласованных structured replies (ответы
сопоставляются по 64-битному handle) — реализован конвейер: заголовки
декодируются последовательно (поток байтов, WRITE-payload идут по порядку),
а файловые операции и ответы исполняются воркерами параллельно (до 32 на
коннектор, `sync.Pool` буферов, байч-флеш ответов при обнулении счёта
in-flight; FLUSH сливает все воркеры). Простые (structured-off) клиенты
сохраняют старый serial-путь. Тесты: out-of-order ответы (медленный read
отвечается последним), FLUSH-барьер, `-race` зелёные.

Добавлено: `-pprof :6061` в sdsd; `-conns N` и приём ответов по handle
(без FIFO) в sdsbench.

Замеры после фикса (vol0 6G rep3, тот же шумный стенд, Fedora):

| Режим | Было | Стало | Vitastor rep3wb |
|---|---|---|---|
| randread 4K qd128 ×1 conn | 10.4K | **52.8K** | — (у них ~32K/conn) |
| randread 4K qd128 ×4 conn | 41.6K | **171–177K** | 129K |
| randread 4K qd32 ×4 conn | 22K | 55.2K | — |
| randwrite 4K qd128 ×4 conn | 22.1K | **63.2K** | 22.3K |
| seqread 1M qd16 ×2 conn | — | 1.6 GB/s | — |

randread QD128: **173K против 129K у Vitastor — обогнали на 34%** на том
же диске в том же шуме. p99.9 12.7–14.8 ms. randwrite 63K — конвейер
ускорил и запись (была та же последовательная передача). CPU-профиль под
нагрузкой 173K: 48% time в syscall (pread/write/epoll) — путь уходит в
ядро, резонный следующий шаг io_uring-батчинг в store.

## Потребление памяти и CPU (замер на 192.168.1.100, sudo)

Сэмплер `mon.py` (RSS из /proc, CPU из /proc/PID/stat, тред-кадрили 2 Гц)
во время прогонов qd128 ×4 conn, 3 OSD rep3 в одном процессе sdsd. Хост
по-прежнему шумит LLM-инференсом — CPU-доли завышены фоном, абсолютные
RSS честные.

Первый замер (до фикса пулов) вскрыл проблему: RSS сервера под randread
доходил до **1.15 ГБ**, heap-профиль показал 1054 МБ в `bufio.NewRead/WriterSize`
— пул `sdsnet.Pool` клиента был без `Limit` (0 = без лимита) и под QD512
диал по TCP-соединению на каждый in-flight запрос: 4112 коннекторов
(5658 fd) × 256 КБ буферов ≈ 1 ГБ. Данные тут ни при чём — раздувала
счётчик соединений, а не полезная нагрузка.

Фикс: `client.Cluster` ограничивает пул на OSD (`SetPoolLimit`, по
молчанию 64 соединения; `pkg/client/client.go`). Глубокие очереди живут
в read-воркерах NBD и на OSD, а не в по-запросных коннекторах клиента;
64 коннектора на цель держат ~10× пика одного хоста (коннектор
сериализует ~14K ops/s).

После фикса (те же прогоны):

| Режим | IOPS | RSS sdsd (сред/макс) | CPU sdsd | RSS клиента | CPU клиента |
|---|---|---|---|---|---|
| idle | — | 11–180 МБ | 0.1% | — | — |
| randread 4K qd128×4 | 175.5K | **112 / 138 МБ** | ~23 ядра | 38 МБ | 1.9 ядра |
| randwrite 4K qd128×4 | 73.9K | **170 / 178 МБ** | ~25 ядер | — | — |

Память: **1.15 ГБ → ~140 МБ (в 8 раз меньше)**, IOPS не упали (randread
175K, randwrite вырос 67→74K — меньше syscall на установку соединений).
Соединений sdsd под нагрузкой: ~390 установлено (было 4112).
QD1 latency: randread 165 мкс p50 148, randwrite 278 мкс p50 262 (в окне
шума, раньше было 89/231 — переснять на тихом хосте).

Вывод: sdsd на 3 OSD rep3 стоит ~150 МБ RAM и берёт ~23–25 ядер на 175K
IOPS (репликация fan-out 3× — основная доля CPU; 48% времени в syscall,
следующий шаг io_uring-батчинг снижает и CPU).

## VDUSE: отладка на стенде (sudo, хост 192.168.1.100)

Демон sdsd поднимает VDUSE-устройство, ядро (`vduse`+`virtio_vdpa`)
превращает его в `/dev/vda`. Прикрепление (`vdpa dev add`) проходило —
ядро доводило статус-машину до `DRIVER_OK` и слало скан разделов, но
`/dev/vda` не появлялся, а задачи уходили в D-state.

**Корневая причина (найдено по исходникам ядра 7.2.11):** при сбросе
устройства `vduse_dev_reset_vqs` обнуляет `vq->kickfd`. `virtio_dev_probe`
вызывает `virtio_reset_device()` ДО вызова драйвера — то есть kick-евентфайлы,
выданные при создании устройства, к `DRIVER_OK` уже «мёртвые». Дальше
`vduse_vq_kick` не сигналит в наш fd, а лишь ставит `vq->kicked` — очередь
нами не дропается, I/O виснет вечно.

**Фикс (commit 2cffa8f2):** на `DRIVER_OK` заново назначаем kick-евентфайлы
через `VDUSE_VQ_SETUP_KICKFD`; ядро само реплеит накопленные kicks
(`vduse_kickfd_setup` при `vq->ready && vq->kicked`). Полностью соответствует
поведению libvduse (назначение kickfd на старте vhost-dev).

**Операционные грабли стенда:**
- Убивать демон при незакрытых I/O нельзя: незавершённые запросы оставляют
  D-state задачи, `vdpa dev del`/`modprobe` вешаются, подсистема vduse мертва
  до перезагрузки. При неудаче — только наблюдение и чистый `reboot`.
- `pkill -f new-sdsd` по ssh убивает собственную сессию (паттерн попадает в
  командную строку ssh) — использовать `pkill -x`.
- Протокол прогонов: поэтапно (демон → `dev add` + 60 с наблюдения → dd),
  fio/VM только после успешного dd.

## Реконнект демона к живому устройству (2026-11-09, commit bb64488d)

Реализовано и проверено на железе: демон переживает kill/restart и
подключается к существующему `/dev/vduse/<имя>` — устройство и vDPA-устройство
переживают смерть демона.

Что делает attach:
- `VDUSE_VQ_GET_INFO` — кольца (desc/avail/used), `avail_index`, `ready`
  (ядро хранит `avail_index` и оно для VDUSE не растёт — использовать для
  «пропуска» нельзя);
- заново `VDUSE_VQ_SETUP_KICKFD` — ядро реплеит накопленные kicks;
- полный `IOTLB_GET_FD`-pull таблицы (драйвер virtio-vDPA НИКОГДА не шлёт
  `VDUSE_UPDATE_IOTLB`, всё через DMA API) + дожим по промаху (pull-on-miss).

Драйвер шлёт запросы ДО готовности очереди (probe/GPT) и ядро эти kicks
теряет — поэтому дроп «всего, что лежит в avail» обязателен на старте и на
reconnect. Пропускать нельзя: у virtio-blk нет blk-mq timeout, незавершённый
запрос навечно держит lock на странице → висит любой `open()` блочного
устройства, `vdpa dev del`, `virtblk_remove`.

**Фундаментальное ограничение ядра (доказано стаком и исходниками):** при
закрытии fd демона `vduse_dev_release` снимает все IOTLB-домены — страницы
guest-буферов освобождаются, а записи таблицы остаются. Запросы, бывшие в
полёте в момент смерти демона, завершить НЕВОЗМОЖНО: чтение desc/запись в
used-кольцо дают SIGBUS. Ни один демон (наш, libvduse/Vitastor/QEMU) этого не
может. Следствие: плановая перезагрузка демона безопасна, когда I/O в полёте
нет (guest.quiesce → restart); kill посреди I/O клинически вешает гостевой
диск до перезагрузки хоста.

Наш демон теперь это переживает: дроп идёт под `SetPanicOnFault+recover` —
SIGBUS перехватывается, кэшированные отображения повреждённого запроса
сбрасываются, запрос завершается `VIRTIO_BLK_S_IOERR` + IRQ, демон продолжает
работать. Стаки падения печатаются с этапом (`stage=next-avail|read-chain|…`)
и снимком IOTLB.

## 4K randread: барьер-фикс + local-direct (2026-11-09, new-sdsd6/7)

**Барьер-фикс (vring.go PushUsed, StoreLoad) — ПОДТВЕРЖДЁН на железе:**
30-секундные фризы randread исчезли полностью (max clat 64–94 мс вместо
30.2 с). Профиль: 80K IOPS = базовый уровень до фризов восстановлен.

**GOMAXPROCS=8 ОБЯЗАТЕЛЕН:** на 64-ядерном хосте дефолтные 64 proc'а дают
50% CPU в runtime.stealWork/findRunnable (шторм планировщика) — это и было
причиной «регресса» 40K. С GOMAXPROCS=8: 80.1K.

**local-direct (socketpair вместо loopback-TCP для локальных OSD):**
новый транспорт в pkg/sdsnet (Socketpair/ServeConn/NewConn/Pool.Local),
Cluster.SetLocalDial, проводка в unistord для всех hosted OSD. Протокол,
QoS, фенсинг, метрики — идентичны TCP-пути. Linux-бенчмарк пакета:
4K op 22.7µs (TCP) → 4.0µs (local), ×5.7.

Матрица на new-sdsd7 (GOMAXPROCS=8, fio /dev/vda, qd128×4 jobs, 20s):

|----------------|-------------|----------------------|----------|
| 4K randread    | 80.1K       | **91.6K** (+14%)     | 175K     |
| 4K randwrite   | 33.8K       | **39.1K** (+16%)     | —        |
| 4K randread qd1| ~300µs      | **127µs** (6.5K IOPS)| —        |
| 1M qd1 r/w     | 103/84      | 85/76                | —        |

1M qd1: A/B-проверка на sdsd6 дала те же 103/84 — падение против прежних
270/270 средовое (том полностью аллоцирован предыдущими бенчами, рейд1 с
rmapbt=0), к local-direct отношения не имеет. Профиль 1M: демон полупростой
(9.2s выборки за 12s) — путь latency-bound, не CPU.

Профиль 91.6K randread: Syscall6 упал с 55% до 46% CPU. Остаток: IOTLB
Lookup (pull-on-miss на unix-сокетах), memmove (2 копиру 4K-плейлоада),
netpoll/wake-цепочки. Следующие шаги: батчинг RPC (N опов на раунд-трип),
zero-copy IOTLB-кэш, XROW-репликация, multi-queue VDUSE.

**Batched RPC (OpBatch + микро-батчер на клиенте), new-sdsd8/9:**
Протокол: OpBatch (N опов на раунд-трип,协商 Value=1, legacy-пиры

микро-батчер per-(volume,OSD): окно 64 слота / 15µs, intake 512,

## 10 ноя, день 2: аппаратная деградация NVMe и восстановление

**Симптом:** randread через стек упал до 16.2K; сырой fio на /dev/nvme0n1
давал 371 IOPS, на nvme1n1 522 (норма 300K+). SMART/температура/PCIe в
норме; в dmesg серии `nvme nvmeX: I/O tag N QID N timeout, completion
polled` на обоих P4510 — классический APST-стоп (уход контроллера в
deep-sleep и зависание на пробуждении). Один MCE (L3/GEN SRC) в dmesg
совпал по времени с vdpa-клинчем 10.11 — клинч объясняется блокировкой
демона на мёртвом диске, не нашей логикой.

**Лечение:** `nvme_core.default_ps_max_latency_us=0` +
`/etc/modprobe.d/nvme-apst.conf`. Грабли Fedora 44: grubby пишет BLS,
но загрузчик берёт строку из GRUB_CMDLINE_LINUX (/etc/default/grub) —
нужен sed по нему + `grub2-mkconfig` + reboot. После ребута
`/sys/module/nvme_core/parameters/default_ps_max_latency_us == 0` —
подтверждено.

**После фиксации:** nvme0 307K, nvme1 310K, LV sustained 404K randread.

**Ложная тревога:** сразу после старта демон давал 2.9–4K IOPS.
Причина — осиротевшее ядровое VDUSE-устройство sds-vol0 (демон убит,
устройство в sysfs живо, все I/O в нём навечно в D). Новые запуски с
именем vol0 цепляли мёртвое имя. Лечение: запуск под новым именем
(sds-vol1) + `vdpa dev add`. Разрушить осиротевшее устройство из
пользовательского пространства нельзя (unbind виснет, destroy ioctl
EINVAL) — только reboot. Правило стенда: **убивать демон можно только
после `vdpa dev del`**, иначе стенд требует перезагрузки.

**Итог по цели 175K:** текущий потолок на стенде ~95K randread при
CPU 520%/800% (не CPU-упор). Следующие шаги: zero-copy IOTLB,
multi-queue VDUSE, сокращение goroutine-хопов на путь ответа.
