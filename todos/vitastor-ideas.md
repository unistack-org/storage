## 1. P0 — Хаос-тестирование в CI (главный урок всех ченджлогов)

Тема №1 у Vitastor в 3.2.0–3.2.3: они **перестали находить баги людьми** и
перешли на детерминированную симуляцию с сидами. В 3.1.0 у них падало 83–97
симуляций из 200 — они это показали публично. Наш `pkg/replication/chaos_test.go`
— зачаток, но без сидов, без power-loss и без модели согласованности.

- [ ] **1.1 DST-хаос блочного слоя с сидами** (`pkg/journal`, `pkg/store`, `pkg/osd`)
      — модель: (а) completion'ы io_uring приходят out-of-order / с задержкой;
      (б) «выключение питания» = случайная потеря части volatile-кэша;
      (в) запись приземляется целиком / частично / обрезанной. После каждого
      power-loss проверяем модель записанных данных, включая битмапы.
      24 конфигурации: store old/new × fsync on/off × csum none/4K/16K ×
      instant/two-phase. 200 сидов на сборку в CI, repro по `--seed N`.
      `[3.2.0, 3.2.1, 3.2.2]` — *самый большой рычаг из всего списка*.
- [ ] **1.2 PG/replication-хаос** (`pkg/osd`, `pkg/replication`) — то же, но
      модель OSD-логики по каждой PG и модель согласованности блочного
      хранилища: инварианты «нет потери подтверждённой записи», «нет
      double-claim», «нет чтения частичного блока как целого». `[3.2.3]`
- [ ] **1.3 Клиентский и сетевой хаос** (`pkg/client`, `pkg/sdsnet`) — обрывы,
      переупорядочение, задержки, stale epoch, full journal → EAGAIN,
      смена epoch во время запроса. Это их следующий шаг, мы можем сделать
      сразу после 1.2. `[3.2.3, plan]`
- [ ] **1.4 Библиотечный test-harness + регресс-тест на каждый фикс.** У них
      62 функциональных скрипта; правило: каждый исправленный баг = тест.
      Завести `storage/tests/chaos/` с общим harness'ом. `[инфраструктура repo]`
- [ ] **1.5 Регулярный LLM-обход кода на баги с последующим фиксом+тестом.**
      В 3.0.14 они закрыли >50 багов, большинство нашли Claude/GPT. Формат:
      отдельный прогон по `pkg/` с требованием минимального repro-теста. `[3.0.14]`

## 2. P1 — Путь записи: write intent + атомарные записи (цель WA → 1)

Содержание презентации Highload'2025. Их путь: 128 KB объекты + 36 B
меты/объект (~290 MB меты на ТБ, ×2 в RAM) → журнал-кольцо → WA 3–5× на 4K →
отказ от LSM (compaction поднимает WA) → **LSMeta** (буферная область вместо
журнала, hashmap + linked lists в RAM, GC по учёту мусора) → + **Write
Intent** на атомарных записях NVMe. Итог: WA ≈ 1.0, 176K randwrite 4K
(~1.75×), латентность 2×-записи та же ≈ 29 µs.

- [ ] **2.1 Write Intent Journal** (`pkg/journal`, `pkg/osd`) — перед записью
      данных пишем на журнал намерение: «сейчас обновлю блок X, новый CRC=Y».
      При восстановлении: записи данных нет/ CRC не совпал ⇒ считаем блок
      старым. Лечит torn writes **без** двойной записи и без отката целого
      диска. Это же — ответ на их «HAS_INCOMPLETE»-класс багов. `[hl2025, 3.0.0]`
- [ ] **2.2 Детект атомарности устройства** (`pkg/store`): читать AWUPF
      (Atomic Write Unit Power Fail) + supported write size; писать через
      `RWF_ATOMIC` при наличии. Реальность по дискам: Micron 7450/7500 = 256K,
      Kioxia CD7/CD8-R = 256K, **Samsung PM9A3 = 0** (т.е. у нас на стенде
      атомарного размера нет), 4K атомарен везде. Linux ≥ 6.11. Важная
      оговорка из их 3.0.1: флаг `RWF_ATOMIC` в ядре был сломан и они его
      отключили — важна именно атомарность при power-loss, а не флаг.
      Сделать `unistorage probe-disk` с выводом AWUPF. `[hl2025, 3.0.1]`
- [ ] **2.3 Метр write amplification в sdsbench** — считать WA (записано на
      диск / записано клиентом) и печатать в отчёте. Без числа мы не увидим
      эффекта от 2.1/2.2. `[hl2025]`
- [ ] **2.4 Упаковка journal-записей** (packing записей в блоке) — у них это
      дало WA с 4–5 до 3.x дёшево. У нас заголовок записи 16 B
      (seq/len/crc) — посчитать плотность на 4K и упаковать мету пачками.
      `[3.0.x]`
- [ ] **2.5 In-memory индекс меты + log-structured мета** — у них цель
      663/371/152 MB RAM на ТБ (сырьё+btree+журнал / +11% / +18% худший
      случай) и ключевое правило: **все записи одного объекта в одном блоке
      меты**, иначе потеря одного блока меты = «выбросить весь диск». Нашу
      строку роадмапа («In-memory мета-индекс объектов», ~512 МБ/ТБ при блоке
      128K, журнал тоже в RAM) оформить как ADR с их числами 663/371/152 МБ
      и инвариантом «один объект — один блок меты». `[hl2025]`
- [ ] **2.6 Расширения, которые они хотят, и которые стоит заложить в формат
      меты сразу** (дешевле сейчас, чем миграцией потом): tombstones (атомарное
      удаление + discard), динамический размер блока, сжатие, локальный
      SSD-кэш (bcache-подобный). `[hl2025 «хотелки»]`

## 3. P1 — Производительность: закрываем randread 41.6K → ≥100K

У нас в [bench-stand.md](./bench-stand.md) единственный большой разрыв —
randread QD128: 41.6K против их 128K (×3). Their bottleneck = CPU + сеть, не
диски (у них 4.27M IOPS rep1 T12Q128 по RDMA, линейные 13–16 GB/s).

- [x] **3.1 Чтение с любой реплики** — сделано (2026-11): порядок предпочтений
      «локальный → наименее загруженный → порядок pg-строки» в
      `Volume.orderReadRefs` (`pkg/client`), счётчик `Pool.Inflight`/`Pool.Ops`
      в `pkg/sdsnet`, хуки в put-чтении и в цепочке снапшотов; unistord
      объявляет хостимые OSD локальными (`SetLocalOSDs`). Тесты
      `pkg/client/replica_read_test.go`. Флаг локальности для DC — отдельно.
- [ ] **3.1b Флаг локальности чтения** (`pkg/client`) — опция в духе их
      `local_reads`: запрещать чтение через меж-DC линк (degraded-чтение
      разрешено, обычный трафик — только локально). Поверх готового
      `orderReadRefs`. `[3.0.x]`
- [ ] **3.2 Кэш-индекс меты в клиенте/OSD** — снять lookup из пути чтения
      (следствие 2.5); на loopback 4K randread уже даёт 171–177K, значит
      узкое место — не диск. `[hl2025]`
- [x] **3.3 `MSG_ZEROCOPY` с порогом** (`pkg/sdsnet`) — сделано:
      `StreamConfig.ZerocopyThreshold` (0 = выкл), TCP-only, кэш проб-запроса
      SO_ZEROCOPY;
      Linux: sendto(MSG_ZEROCOPY)+MSG_ERRQUEUE-синхронизация, авто-fallback
      на kernel copy; другие ОС/TLS — обычный путь. `[3.0.x]`
- [x] **3.4 Клиентские I/O-потоки** (`pkg/client`) — сделано: `sdsnet.Stream`
      (pipelined: writer-горутина батчит кадры, reader сопоставляет по seq,
      окно backpressure, ctx/дедлайны на оп, protocol-ошибки не убивают
      стрим); приём через io_uring — `store.Options.AsyncRing` (см. §1). `[3.0.x]`
- [ ] **3.5 Клиентский writeback-буфер** (`pkg/client`) — `client_enable_writeback`.
      Важно и для честности бенча: без writeback их rep3-запись падает до
      3.4K IOPS QD32, а наш hard-режим сравнивать с их writeback-режимом
      некорректно → в бенче прогонять оба режима. `[3.0.x]`
- [ ] **3.6 `cpubench`-аналог** (`storage/bench/cpubench`) — цена чексумм и
      шифрования на ядро: у них xxhash3 1M ≈ 104 GB/s, AES-XTS+GCM
      ≈ 12.6 GB/s на EPYC. Без этого числа нельзя включать csum/шифрование
      на горячем пути (см. §5, §6). `[bench inventory]`
- [ ] **3.7 Матрица бенча как у них** — T1Q1 / T12Q128, TCP и RDMA, rand +
      seq, репликации rep1/rep3; `fio_blockstore`-подобный микро-бенч слоя
      меты в обход сети. Наш `crushkv` placement-бенч сохраняем и
      документируем как наш отличительный артефакт — у них такого нет. `[их repo bench2]`
- [ ] **3.8 NFS-подобный read-ahead для нашего файлового/VDUSE-пути** — у них
      read-ahead дал 2–3×. Применимо к `pkg/vduse` и будущему FUSE. `[3.2.x]`

## 4. P1–P2 — Семантика, ENOSPC, recovery

- [x] **4.1 Режимы `immediate_commit`: `flush` / `journal` / `none`** + lazy
      fsync (батчинг fsync) — сделано: `-commit none|flush|sync|journal` +
      `-fsync-batch` в `pkg/store`/`unistord`; journal = WAL с ack по
      fsync журнала, фоновое разглаживание, replay при старте. Тесты
      «подтверждённая запись не теряется при power-loss» —
      `pkg/store/journal_test.go` (crash survival, torn tail, remove
      checkpoint). Не делал: `small_write_throttling` (нет demand). `[2.x, 3.0.x]`
- [x] **4.2 ENOSPC и полный журнал** (`pkg/store`, `pkg/osd`, `pkg/client`) —
      сделано: guard-rail free-space в `pkg/store` срабатывает раньше kernel
      ENOSPC и отдаёт `StatusNoSpace` (OSD остаётся живым); journal-режим:
      ENOSPC журнала → backpressure applier'а, клиент ретраит (не виснет);
      предупреждение «диск >95%» в `unistorctl status`; предупреждение и
      метрика свободного места. Тесты ENOSPC в `pkg/store`. `[3.0.x]`
- [ ] **4.3 `recovery_tune_interval`** (`pkg/client` + монитор) — автоматическое
      регулирование скорости recovery/rebalance по влиянию на клиентский I/O;
      приоритет клиентского трафика над восстановлением. Частично: приоритет
      клиента обеспечен (recovery/vacuum paced QoS-лимитером ниже клиентского
      I/O, темп задаётся вручную лимитом); автоподстройки по задержкам клиента
      нет. `[3.0.x]`
- [ ] **4.4 `noout`/`pg_minsize` в CLI + `describe`** — операционный доступ к
      уже реализованной семантике (см. §7). Частично: `min_size` — флаг
      `unistord -min-size` + параметр `vol create` (кворум, fast-fail
      ErrDegraded); `describe` = `unistorctl vol info`; `noout` — только
      библиотечный `SetOutTime(0)`, в CLI не выведено. `[2.3.x]`
- [x] **4.5 Онлайн-resize экспорта** (`sds-nbd`, `pkg/vduse`) — рост размера
      на лету у NBD/VDUSE/QEMU + online expand в CSI. Реализовано: размер в
      transmission больше не фиксируется при `CmdGo` — `cs.size` атомарный и
      обновляется из бэкенда при запросе за старую границу (checkRange),
      рост через `unistorctl volume resize` обслуживается следующим же
      запросом без реконнекта (тест TestOnlineGrowServedWithoutReconnect);
      VDUSE уже сообщал рост гостю за ~2 с (watchCapacity/SetCapacity).
      Уменьшение под живым гостем в NBD небезопасно по протоколу — только
      через реконнект. Online expand в CSI — вне нашего репозитория. `[3.2.x]`

## 5. P2 — Пакет безопасности (их 3.1.0 = «security release»)

Порядок по полезности для нас, от дешёвых к дорогим:

- [ ] **5.1 TLS/mTLS к meta/etcd** + поддержку DNS-имён в адресах (`pkg/meta`).
      У них не было TLS на etcd до 3.1.0. `[3.1.0]`
- [ ] **5.2 Транспортное шифрование AES-GCM: по умолчанию только заголовки**,
      данные открыты (быстро), опция — шифровать всё. Это их компромисс по
      цене, и он правильный: см. 3.6 (12.6 GB/s на AES).
      Наш `pkg/sdsnet` сейчас не шифруется вообще. `[3.1.0]`
- [ ] **5.3 Транспортные чексуммы xxh3: по умолчанию только данные**, опция —
      только заголовки; отдельная опция дисковых чексумм `xxh3_32` +
      проверка при чтении. У нас CRC есть только в журнале. `[3.1.0, 3.2.x]`
- [ ] **5.4 E2E шифрование тома AES-XTS** + хранение ключей в Vault
      (с ретраем по таймауту). В нашем коде крипто-лойера нет нигде
      (`pkg/object`, `pkg/store`, `pkg/sdsnet` чистые) — закладывать сразу
      как отдельный слой между `pkg/store` и клиентом, с ключом на том.
      Позиция уже есть в Phase 6 роадмапа («AES-256-XTS»). `[3.1.0]`
- [ ] **5.5 Аутентификация по сертификатам и ACL пользователей**, enforced
      **и в meta, и в OSD** (у них ровно это и было исправлением: ACL
      обходились на OSD). `[3.1.0]`
- [ ] **5.6 Мелочи клиента, спасающие прод**: fatal-error режим вместо
      `exit(1)` (чтобы не убивать QEMU), DNS-retry при сбое разрешения
      meta-адресов, `use_sync_send_recv` (клиент без io_uring). `[3.1.0, 3.2.x]`

## 8. Research / дальний прицел (не тудушки, а направления)

- **Свой KV вместо etcd.** Vitastor сделал Antietcd (встраиваемая замена
  etcd, Jepsen-проверенная сериализация в 3.0.2) и ушёл от внешнего etcd —
  из-за нагрузки на etcd при флэппинге PG (см. 1.6) и из-за зависимостей.
  Наш `pkg/meta.Store` уже абстракция: держать DirStore, готовить переход на
  собственный raft-лой, когда etcd станет узким местом.
- **Блочное хранилище поверх объектного / свой FS.** У них два пути (1.5.0:
  VitastorFS + параллельная оптимистичная Б-дерево KV). Для UniStack это
  длинный хвост — не в ближайших двух фазах.
- **BCache-подобный локальный SSD-кэш** (их «хотелка» в презентации) —
  интересно для гибридных стендов UniStack.

## 9. Что сознательно НЕ берём

| Их фича | Почему не берём |
|---|---|
| S3-шейп (Zenko) | Экспериментально у самих авторов; вне нашей цели «блочный сторадж» |
| VitastorFS / свой POSIX FS | Отдельный проект на годы; у UniStack свои задачи |
| Antietcd сейчас | etcd работает; меняем только когда он станет доказанным узким местом |
| RDMA-слой (RoCE, QoS) | На нашем стенде 25GbE-эквивалента нет; сначала закрыть randread по TCP |
| ublk вместо VDUSE | ublk интересен (у них дефолт в CSI), но VDUSE уже написан — сначала довести до конца Linux e2e |
| loro-библиотека / C++ клиент | У нас Go-only принцип, он же наше преимущество в обслуживании |
