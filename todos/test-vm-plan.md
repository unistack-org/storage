# TEST-VM PLAN: сторадж для тестовых виртуалок без гарантий (2 ноды, 4 NVMe)

Цель этого документа — ответить на вопрос: **что нужно сделать, чтобы этот
сторадж можно было отдать под тестовые виртуалки, на которые нет никакой
гарантии**, на железе «2 ноды, суммарно 4 NVMe», и чтобы при этом были:

1. загрузка blob'а диска в сторадж по HTTP,
2. снапшоты,
3. бекапы,
4. выгрузка (экспорт) диска по HTTP на скачивание,

плюс зафиксированная форма поставки: **два бинарника — демон и контрол**
(имена зафиксированы владельцем: `unistord` — демон, `unistorctl` — контрол).

> **Статус (обновляется по мере реализации).** Сделано в коде:
> M0.1, M0.2, M0.3 (ENOSPC end-to-end: store→OSD→клиент→NBD, `-ENOSPC` гостю),
> trim/discard, M5-QoS полностью: лимиты IOPS/Bps на том (клиентская пара,
> «едет» с томом), агрегат на диск (`-osd-qos`), пер-экспорт (`-qos`),
> именованные классы (`-qos-class`, QoSTemplate у тома), **смена QoS
> горячая — для уже открытого тома** (meta-watch, без перемонтирования;
> админ = отсутствие класса = без лимитов), идемпотентный SetQoS
> (не раздаёт burst на каждый watch-ивент). Бинарники: `cmd/unistord`
> (бывший `sdsd`) + новый `cmd/unistorctl` (vol ls/create/rm/info/qos/
> import/export, qos ls/put/rm, osd ls; import с `http(s)://` URL,
> export sparse). **M2 (HTTP-контур) — служебный HTTP демона
> (`unistord -http 127.0.0.1:8443`, `cmd/unistord/admin.go`): healthz,
> status, osds, тома CRUD, QoS тома и классов, import телом
> (`application/octet-stream`, `?offset=`) и по URL (демон качает сам),
> export потоком `octet-stream` с точным `Content-Length` (дыры → нули,
> скачанный образ восстанавливается на диск как есть). Проверено e2e на
> живом 2-OSD кластере: побайтовая сверка импорта/экспорта, коды
> 400/404/409.** Попутно найден и исправлен реальный баг: закрытие
> meta-watch (`dirWatcher.Stop`) паниковал «send on closed channel» на
> последующих записи — канал событий больше никогда не закрывается,
> наблюдатель снимается с регистрации; регрессионные тесты с `-race`.
> **M6.2 решён и реализован: встроенный raft-KV (вариант (c), решение
> владельца — raft сразу; финальная реализация — ядро etcd-io/raft,
> вариант (e), по решению владельца).** `pkg/meta/raftstore.go` поверх
> `go.etcd.io/raft/v3` (библиотека, NOT внешний etcd-сервер): флаги
> `-raft/-raft-dir/-raft-peers`, свидетель = узел `-raft` без `-osd`/
> `-export` (третья слабая машина даёт кворум); та же `meta.Store`
> (CAS/Watch) поверх FSM-snapshot. При потере кворума — **только чтение**
> (записи 503 «no quorum»; операторский HTTP живёт: статус, чтение томов,
> экспорт). Запись, пришедшая не лидеру, форвардится лидеру
> (`-raft-proxy`/`-raft-proxy-peers`) с read-your-writes — узел ждёт, пока
> применит индекс у себя, прежде чем вернуть успех. E2E-трио проверено
> живьём: создание/QoS/импорт/экспорт через любой узел, потеря 2 из 3 →
> 503 на запись + чтение и экспорт работают, ре-джой и возобновление
> записи. **Бейк-офф по запросы владельца «может, etcd пакет?»: сравнили
> embedded etcd (spike: `meta.Store` поверх `embed.Etcd`, 3 ноды, тесты
> зелёные) с текущим raft — вывод: оставляем raft** (etcd: 1053 модуля
> против 135, бинарь ×2.2, линеаризуемые чтения умирают с кворумом).
> Подробности — §M6.2-бейк-офф. Проанализирован и вопрос «есть ли рафт-либа
> поменьше»: единственная живая лёгкая — etcd-io/raft (14 модулей, ядро etcd
> без транспорта/лога) — **миграция выполнена (опция (e), реализована)**:
> +400–600 строк нашей обвязки написаны, ядро — etcd-raft v3.7.0. «Свой мини-raft»
> (путь antietcd) — вариант (g): ядро = 7.8k строк + Jepsen-класс тестов,
> наш ответ на минимализм — тоже (e), а не своё ядро (§M6.2-бейк-офф,
> часть 2).
> Остальное ниже — план.

Это прикладной план поверх [roadmap.md](roadmap.md): он не дублирует фазы,

## 1. Что уже есть и почему это уже почти работает

Есть (проверено в этом плане, не «на глаз»):

- Полноценный clustered-путь: `unistord -cluster <meta-каталог> -osd id@dir@addr
  -crushmap -epoch -create имя:размер -export имя=том` — 3 OSD в процессе,
  CRUSH-размещение, кворум, epoch-fencing, thin-чтение нулями, trim,
  hard-семантика (деградация = пауза, а не ошибка), `out_time` + пробер.
- Экспорт в гостя: NBD (полный: flush/trim/write-zeroes, structured replies)
  и VDUSE (Linux/KVM).
- `pkg/meta` — интерфейс формы etcd: `Get/Put(cas)/Delete/List/Watch`. То есть
  `Delete`/`List` для томов были готовы с самого начала, не хватало только
  обёрток и аллокатора OID.
- Тесты: roundtrip, кворум с мёртвым OSD, stale epoch, hard-mode восстановление.

Не было ничего из того, что требует «отдать чужим ВМ»: HTTP-контура,
аутентификации, квот, снапшотов, удаления тома, ENOSPC-ветки, метрик.

## 2. M0 — Блокеры (без них отдавать нельзя)

### M0.1 ✅ Приватный диапазон object-id на каждый том

**Найдено и исправлено в рамках этого плана.** Было:

```go
func (v *Volume) oid(index uint64) uint64 { return index + 1 }  // OID = индекс в томе
```

при том, что OSD принимает имя экспорта и **игнорирует** его
(`pkg/osd` `objectBackend`: «one OSD serves the object namespace it owns,
objects are namespaced by OID, volume routing is the client's job»), а клиент
соединяется со всеми OSD с одним и тем же именем экспорта `"vol"`. То есть
том `vm-a` и том `vm-b`, размещённые на одних и тех же OSD (а на 4 дисках
они гарантированно размещены на одних и тех же), адресовали **одни и те же
файлы**: запись во `vm-b` на смещении 0 затирала `vm-a` на смещении 0.
Одна ВМ молча портила диск другой. Для нашего полигона это был единственный
блокер архитектуры, и он решён.

Решение — **глобально уникальный OID-бейз на том** (как у Vitastor/Sheepdog,
а не «namespace в заголовке запроса»):

- `meta.VolumeSpec.OIDBase` — первый id приватного диапазона тома;
  объекты тома лежат в `OIDBase+1 .. OIDBase+NumObjects(Size)`.
- `meta.NextOIDBase(ctx, store, count)` — кластерный аллокатор на CAS-эволюции
  ключа `alloc/oids`: конкурентные создатели томов не получают пересекающихся
  диапазонов, резервирование переживает рестарт, `NilOID = 0` по-прежнему
  зарезервирован (диапазоны начинаются с 1).
- `Volume.oid(index) = spec.OIDBase + index + 1`.
- `OpenVolume` отказывает тому без `OIDBase` (явная ошибка «пересоздай»),
  а не тихо читает чужие объекты.

Почему бейз, а не поле в протоколе: `ReqHeader` — 32 байта и в нём нет места
под namespace, а бейз даёт изоляцию **без изменения провода**, без потери
свойства «один OSD = один плоский каталог объектов», и бесплатно предоставляет
то, что нужно дальше: снапшоты = `OIDBase + gen*NumObjects + index + 1`,
клон = копия меты со своим бейзом. Цена: 64-битное пространство id должно
жить долго — 4 МиБ-объекты, `2^64` id = 7×10¹³ ТБ, с запасом.

Регресс-тест (обязательный, в CI): `pkg/client/twovolume_test.go`
`TestClusterTwoVolumeIsolation` — два тома на трёх общих OSD, писаем в
**одинаковые смещения** в нескольких объектах, сверяем байты, проверяем, что
тонкая область не «видит» чужие данные и что trim одного тома не дырявит
другой. `TestClusterVolumeListDelete` — лист/удаление/двойное удаление.
Полный прогон: `GOWORK=off go test ./pkg/...` и `sds-nbd` — зелёные.

### M0.2 ✅ `ListVolumes` / `DeleteVolume`

`meta.ListVolumes`, `meta.DeleteVolume`, `Cluster.ListVolumes`,
`Cluster.DeleteVolume` (с явным комментарием: **объекты не удаляются** —
нужен проход вакуума, M1.4). Без этого контрол-бинарник физически не может
удалить диск ВМ.

### M0.3 Выживание при полном диске / полном журнале (3–5 дней)

Сейчас ни `pkg/store`, ни `pkg/journal` не различают ENOSPC: место кончается →
запись падает generic-ошибкой → клиент в hard-режиме считает это transport-сбоем
(или нет) и поведение не определено. Тестовая ВМ, отожравшая диск, обязана
упереться **в свою квоту**, а не уложить OSD. Нужно:

- `store`: отличать ENOSPC/EDQUOT, не считать объект повреждённым, не падать;
- `sdsnet`: новый статус `StatusNoSpace` (есть свободные биты в wire-протоколе),
  отдельный от generic-ошибки;
- `pkg/client`: ENOSPC от реплики → не «осд умер» (не в `noteFailure`!),
  ошибка вверх гостю как IO-error на этом томе, а всем остальным томам —
  нормальная работа;
- журнал: при полном журнале — EAGAIN-подобное поведение и форс-флеш данных
  (у них это отдельный режим, §4.2 `vitastor-ideas.md`), не падение;
- тест: «диск заполнен на 100% → том A пишет с IO-error, том B работает,
  OSD жив, после освобождения места A пишет».

### M0.4 Квота тома (2–3 дня) — ✅ реализовано

`VolumeSpec.Quota` (>0, <size ⇒ тонкий том с потолком аллокаций; 0/≥size ⇒
как раньше, квота = size, нулевой оверхед). Учёт по аллокационной битовой
карте тома (префикс `allocmap` в meta, гранулярность = объект 4 МиБ):
`writeChunk` заряжает бит при первом касании объекта (CAS-цикл
`meta.MutateAlloc`, кэш в клиенте), полный sparse TRIM объекта освобождает
бит. Превышение ⇒ `ErrNoSpace` (обёрнутый `syscall.ENOSPC`) ⇒ гостю
ENOSPC через NBD. `SetVolumeQuota` меняет квоту на живом томе (watch как у
QoS); уменьшение нерукотворно — читает/перезаписывает уже аллоцированное.
API: `PUT /v1/volumes/{name}/quota`, `vol create -quota`, `vol quota`,
QUOTA/USED в `vol ls`/`vol info`. Отдельный учёт «реальных байт на OSD»
(с репликами) — в M6.

## 3. M1 — Два бинарника (зафиксированная форма поставки)

Решение владельца: **ровно два бинарника**.

```
unistord      — демон данных: OSD + экспорт в ВМ + служебный HTTP на этой ноде
unistorctl    — контрол: CLI управления кластером (meta-каталог)
```

**Реализовано (M1 ✅):** `sds-nbd/cmd/unistord` (переименован из `sdsd`) и
`sds-nbd/cmd/unistorctl`: `vol create/ls/rm/info/qos/import/export`
(import читает файл **или `http(s)://` URL** потоково, export пишет
sparse-образ с дырами, `-` = stdout), `qos ls/put/rm` (классы),
`osd ls` (OSD + epoch карты). Работает прямо по meta-каталогу
(`-meta-dir`), который разделяет с unistord.

### M1.1 `unistord` (один процесс на ноду)

Уже умеет всё данные-ное: `-osd id@dir[@addr]` (повторяемо → 2 NVMe на ноду =
2 OSD в процессе), `-cluster`, `-crushmap -epoch`, `-create`, `-export`,
NBD/VDUSE, `-pprof`. Добавить:

- [x] `-http 127.0.0.1:8443` — служебный HTTP (**это не «ещё один бинарник»**,
      а интерфейс демона): `/healthz`, `/v1/status`, `/v1/osds`,
      `/v1/volumes` (CRUD), `/v1/volumes/{name}/qos`,
      `/v1/volumes/{name}/import` (тело или URL), `/v1/volumes/{name}/export`,
      `/v1/qos/classes`, снапшоты (M3): `POST/GET .../snapshot(s)`,
      `DELETE .../snapshot/{gen}`, `POST .../rollback`. Реализовано в
      `cmd/unistord/admin.go`; карcase —
      тот же `net/http`, что поднимает `-pprof`. Осталось ниже `/metrics`.
- [ ] `/metrics` (Prometheus) — отдельный item roadmap, Фаза 5b §6; полигон
      без метрик слеп.
- [x] `/v1/volumes/{name}/snapshots`, rollback — поверх M3; клон тоже
      сделан: `POST /v1/volumes/{name}/clone`.
- [ ] Аутентификация HTTP: mTLS или статический токен; слушать по умолчанию
      на loopback/management-сети, не на `0.0.0.0`.

### M1.2 `unistorctl` (контрол; далее — клиент того же HTTP API)

**Реализовано (M1 ✅):** CLI работает напрямую по meta-каталогу
(`-meta-dir`), что для 2-нодового полигона с общим meta достаточно.
Следующий шаг — оболочка над HTTP API демона (их опыт: это дало CSI и
дашборды; roadmap Фаза 5b «HTTP API + OpenAPI» — тот же пункт, здесь он
становится обязательным). OpenAPI-спека — артефакт репозитория, по ней
генерируется и CLI, и клиент UniStack.

```
unistorctl vol create vm7 40G -replicas 2 -min-size 1   # ✅
unistorctl vol ls | vol rm vm7                          # ✅
unistorctl vol import vm7 file.raw | http://…/d.img     # ✅ (M2 CLI-часть)
unistorctl vol export vm7 vm7.raw                       # ✅ (sparse)
unistorctl vol qos vm7 -class std                       # ✅ (горячая смена)
unistorctl qos ls|put|rm                                # ✅
unistorctl vacuum [ls|run]                             # ✅ (M1.4)
unistorctl recovery ls|check <vol>|run <vol>            # ✅ (M6.3)
unistorctl vol snap create|ls|rm|rollback <vol> [gen]   # ✅ (M3)
# далее поверх HTTP: backup create (M4),
# node ls|node out|map dump|status
```

Пустые слова в списке (`raw-ls`, `kv-rescue`, `map check`) — их спасательные
инструменты (§6.8–6.9); для полигона нужны `volume *`, `import`, `export`,
`status`, `node out`.

### M1.3 Что остаётся служебным (не «третьими бинарниками»)

`sdsbench` остаётся инструментом бенча (он и есть источник цифр
`todos/bench-stand.md`), не продуктовым контролом. Если нужен тестовый гость
без QEMU — `-nbd`/`-vduse` уже в демоне.

### M1.4 Вакуум удалённого тома (vacuum) — ✅ реализовано

`DeleteVolume` оставлял мусор на OSD. Реализовано как «тумбстон + вакуум» (как autovacuum в Postgres):
`DeleteVolume` пишет в мета заглушку `VacuumRecord{Name, OIDBase,
NumObjs, DeletedAt}` (тумбстоун) и идемпотентен — повторное удаление
отсутствующего тома не ошибка. Отдельный проход `Cluster.VacuumDeletedVolumes`
перечисляет тумбстоуны, обходит каждый OSD (пул с актуальным epoch —
вакуум сам делает `Refresh`, иначе перезагруженные OSD отбили бы запрос
`stale epoch`) и снимает объекты `[OIDBase+1, OIDBase+NumObjs]` с одним
`Sync` на проход; тумбстоны удалённых целиком томов вычищаются из меты.
Триггеры: `unistorctl vacuum [ls|run]`, HTTP `GET/POST /v1/vacuum`
и автовакуум `unistord -vacuum-interval N` (секунды, 0 = выключен).
Полигон: способ освободить место после зачистки — есть.

**Пер-томный вакуум (по имени)** — `unistorctl vacuum run <vol>` и
`POST /v1/vacuum/{name}`. Для удалённого тома снимает только его
тумбстон; для живого тома включает режим live-vacuum: проход по всем
объектам тома, полностью нулевые объекты пробиваются дырами на всех
репликах (эквивалент fstrim снаружи) и освобождают квоту. Предикат
прохода — физическая аллокация файла объекта (`OpStatInfo` протокола:
`st_blocks*512`), а не видимый размер: пробитые/тонкие файлы имеют
размер 4 MiB при нулевой аллокации, поэтому протокол поднят до v3
(OpStatInfo обязателен во всех компонентах — деплой совместный;
сервер без метода отвечает NotSupp, vacuum прерывается честной
ошибкой). Нулевые объекты читаются целиком — запускать в тишине;
повторный проход по пробитым объектам — no-op (аллокация 0).

**Оценка M1: 1–2 недели.**

## 4. M2 — HTTP: залить blob и скачать диск ✅

**Реализовано** в `sds-nbd/cmd/unistord/admin.go` (`unistord -httpAddr`
по умолчанию `127.0.0.1:8443`): import телом `application/octet-stream`
с `?offset=` и import по URL (демон качает сам — для CI с образом в
реестре), export потоком с точным `Content-Length`. E2E-проверено на
живом 2-OSD кластере: импорт двух образов (в начало и в середину тома),
экспорт целиком, побайтовая сверка всех областей. Осталось: resume,
xxh3, аутентификация — ниже они помечены как будущие.

### M2.1 Импорт (загрузка образа диска в том)

`POST /v1/volumes/{name}/import` (chunked body) и `POST /v1/import {url}`
(скачать самим — удобно для CI, где образ лежит в реестре). Механика:

1. размер **объявляется** (`Content-Length`/параметр `size`) — том создаётся
   фиксированного размера, импорт не может вырасти за квоту;
2. пишется через `Volume.WriteAt` **выровненными 4 МиБ-чанками** (последнее
   — хвостом): путь, который уже измерен и не создаёт мелких объектов;
3. resume: `GET .../import/{id}` отдаёт смещение; тело можно продолжить с
   `Range`/`X-Offset` — образ на 40 ГБ через Wi-Fi рвётся;
4. контрольная сумма: xxh3 (зависимость уже есть, `OneOfOne/xxhash`) —
   `Expected` в заголовке, считаем на лету, сверяем в конце;
5. прогресс и отмена по ctx.

Тонкий импорт: пропускать полностью нулевые чанки (`WriteZeroes`/не писать) —
образы обычно разреженные, экономия места и времени ×N.

### M2.2 Экспорт (скачивание диска)

`GET /v1/volumes/{name}/export` → `application/x-raw-disk-image`:

- стримим `ReadAt` по 4 МиБ-окнам **без аллокаций на окно** (переиспользуемый
  буфер — наш стандарт no-alloc на горячем пути);
- пропуск дыр: объект, которого нет (`StatusNotFound`), — это известный
  признак тонкой области; отдаём разреженно (multipart/`tar` sparse) и
  экономим гигабайты;
- Ограничение скорости (rate limit) — скачивание не должно уложить I/O гостям;
- аутентификация токеном, срок жизни ссылки (подписанный URL) — чтобы ссылку
  можно было отдать человеку.

Совместимость: формат **raw** (это и есть «blob диска»). `qemu-img convert`
в qcow2/VHDX — на стороне потребителя; свой конвертер (roadmap Фаза 6
«qemu-img convert-совместимый raw-стрим») — позже.

**Оценка M2: 1–1.5 недели** (импорт+экспорт вместе, с тестами на HTTP-слое).

## 5. M3 — Снапшоты (3–5 недель, объёмная часть) — ✅ сделано

Схема зафиксирована в roadmap (Фаза 6) и в их разборе (§7.1): **forward/redo**
— при снапшоте текущие объекты тома переименовываются в снапшот-поколение,
запись идёт в новое поколение, чтение идёт по цепочке родителей. Никакого
CoW-refcount-графа.

> **Реализовано (ADR: `todos/adr-snapshots.md`).** Вариант без rename:
> снапшот забирает текущий диапазон OID себе, том получает новый свежий
> диапазон (та же арифметика `oid = OIDBase + gen*NumObjects + index + 1`),
> вся координация — атомарные CAS-транзакции meta. Клиент: chain-read
> (`readSnapshotChain`), материализация TRIM после снимка, откат, удаление
> снапшота через вакуум-движок. CLI `vol snap create|ls|rm|rollback`,
> HTTP `POST/GET .../snapshot(s)`, `DELETE .../snapshot/{gen}`,
> `POST .../rollback`. Тесты: meta 7 (`pkg/meta/snapshots_test.go`) +
> клиентские 6 (`pkg/client/snapshots_test.go`) + HTTP
> (`admin_snapshots_test.go`).
>
> **Клоны (вторая половина M3) — сделано** (`pkg/meta/clones.go`): клон =
> копия меты поверх расшаренной цепочки источника (источник замораживается
> дополнительным поколением), свой свежий live-диапазон, QoS/геометрия
> наследуются. Расшаренные диапазоны считаются записями `genrefs:` —
> vacuum удаляемого тома/снапшота/отката обходит те, на которые есть
> ссылка; протокол «нарасти до CAS, сбрось после CAS» даёт только утечки
> при крахе, никогда уничтожение. CLI `vol clone <src> <dst> [-quota]`,
> HTTP `POST .../clone {"name","quota"}` (201/404/409). Тесты: meta 8
> (`clones_test.go`), клиентские E2E 2 (`pkg/client/clones_test.go`),
> HTTP (`admin_clone_test.go`).

Наша выгода от M0.1: поколения — это арифметика над уже существующим бейзом,
`oid(index, gen) = OIDBase + gen*NumObjects + index + 1`. Мета:
`VolumeSnapshots{Name, []Snap{Gen, CreatedAt, Parent}}` + «текущее поколение»
в `VolumeSpec`. Нужны ADR (формулировка решения — обязательный пункт roadmap)
и сразу их грабли в тесты:

- [x] >255 снапшотов ломают чтение (у них был баг — генерация в 8 бит) —
      у нас generation = uint32, монотонный `LastGen` (откат не переиспользует
      id): `TestSnapshotLimitAnd300Gens`, `TestSnapshotRollback`;
- [x] параллельное удаление снапшота из двух процессов рвёт цепочку —
      создание/удаление/откат = CAS-транзакции meta (rev-контент-кашенс):
      `TestSnapshotParallelCreateSerializes`, `TestSnapshotDelete`;
- [x] чтение тома с N родителями по одному объекту: стоимость цепочки, лимит —
      глубина ограничена 64 (`MaxSnapshots`, ERR_TOO_MANY_SNAPSHOTS), чтение
      идёт newest→oldest и останавливается на первом попадании;
- [x] power-loss между rename и записью меты (атомарность: мета = источник
      истины, rename идемпотентен) — у нас rename нет вовсе (ADR): данные
      свежего диапазона пишутся до коммита меты, но становятся видимы только
      с ней — закоммиченный в консенсусе снапшот всегда указывает на уже
      записанные объекты; «сироты» (диапазон записан, мета не закоммичена)
      не видны ни одному тому и собираются `VolumeGarbage` при удалении тома.

Откат (`rollback`) для полигона важнее клона: сломанную тестовую ВМ проще
вернуть, чем чинить. Клон (сверх копий для «партии одинаковых ВМ») — копия
меты + refcount + GC; это вторая половина M3 — **сделана** (см. блок-кавычку
выше: `genrefs`-счётчики вместо графа, GC = существующий вакуум-движок).

**Быстрый суррогат, если M3 задерживается:** не понадобился — M3 сделан.

## 6. M4 — Бекапы (1–2 недели после M3)

- Полный: снимок → дамп в приёмник (`file://`, `s3://`/S3-совместимый,
  `sftp://`) — приёмник как интерфейс, не как хардкод.
- Инкрементальный: даём пары снимков (M3) → сравниваем поколения → пишем
  только изменившиеся объекты; дешевле dirty-bitmap, и не нужен новый
  персистентный битмап на горячем пути.
- Расписание (cron) — на стороне UniStack, не демона: демон предоставляет
  `backup create --base <snap>`.
- Проверка бекапа обязательна: `backup verify` = контрольные суммы +
  контрольная выборка объектов, иначе «бекапы» — это файлы в неизвестном
  состоянии.
- Восстановление = импорт в новый том (M2.1) — тот же путь, что и загрузка.

## 7. M5 — Враждебная гостевая ОС: что нужно, чтобы соседи выжили

«Гарантии никакой» означает: гость будет жрать ресурсы, ломать свою ФС,
пытаться выйти за границы. По пунктам:

1. **Изоляция данных** — M0.1 (сделано) + M0.4 квота. Это фундамент, всё
   остальное — надстройка.
2. **Аутентификация на пути данных.** Сейчас `sdsnet` — это голый TCP:
   нет ни аутентификации, ни шифрования, ни контрольных сумм. Любой, у кого
   есть порт OSD и имя тома, читает и пишет любые тома кластера. Для полигона
   минимум: **токен/ключ в handshake** + сеть, закрытая от гостей (см. п.7).
   Шифрование — решение владельца, roadmap «Риски» п.8 (дефолт AES-GCM
   на заголовки, полный — opt-in).
3. **QoS per-volume** (roadmap Фаза 6 «квоты, QoS»): потолок IOPS/BPS на том.
   Без него одна ВМ с fio в госте сажает латентность всем. Реализуемо дёшево:
   семафор в клиенте/демоне на том + шейпер на OSD; наш `Pool.Limit` уже
   работает как ограничитель конкурентности на цель — та же механика.
   **Реализовано** (`pkg/qos`, token bucket): клиентская пара на том
   (лимит «едет» с томом, кто бы его ни открыл), именованные классы
   QoSTemplate, `-qos`/`-qos-class`/`-osd-qos` в unistord, смена QoS для
   уже открытого тома вживую через meta-watch; админ = без лимитов.
4. **ENOSPC = квота, а не авария** (M0.3) — главный способ, которым гость
   «убивает» сторадж.
5. **Никаких привилегий в госте.** Экспорт — NBD-клиент внутри гостя
   (гость видит `/dev/nbdX`) или VDUSE в хосте (гость видит `/dev/vdX`).
   Для враждебных гостей **предпочтителен VDUSE/хостовский экспорт**: NBD-клиент
   в госте можно убить из гостя (`modprobe -r nbd`), VDUSE-устройство живёт в
   хосте и гость им не управляет. Порядок «сначала довести VDUSE e2e, потом
   ublk» уже зафиксирован (roadmap «Риски» п.7) — здесь он получает второй
   аргумент, безопасности.
6. **Blast radius на ноду.** 2 ноды = 2 домена отказа; демон на ноды —
   единая точка для всех ВМ этой ноды. Обязательные ограничители:
   `-max-conns`, лимиты памяти (у нас есть `-gogc`, `-ballast-mb`), лимит
   очередей на экспорт, watchdog рестарта, и **cgroup-лимит на весь `unistord`**
   в юните (CPU/IO-weight), чтобы тестовый полигон не мог положить хост.
7. **Сеть.** Три плоскости: данные OSD↔клиент (закрытая, между нодами),
   экспорт в гостя (виртуальная сеть, без маршрута до management),
   management HTTP (только loopback/VPN, mTLS). Гость не должен иметь route
   до порта OSD — иначе п.2 не поможет.
8. **Что гость может сломать легально** (зафиксировать в регламенте полигона):
   свою ФС, свои данные, место в своей квоте, свою задержку (пока QoS нет).
   Чего он не должен: чужих данных, чужого места, живучести кластера.

**Оценка M5: 2–3 недели.** MVP для полигона = п.1 (есть), п.3, п.6, п.7
(≈ 1 неделя), аутентификацию data path (п.2) можно вторым эшелоном, если
сеть закрыта.

## 8. M6 — Две ноды, четыре NVMe: реальные ограничения железа

### M6.1 Layout — ✅ реализовано (документ `polygon-layout.md`)

Рабочая конфигурация полигона задокументирована в `todos/polygon-layout.md`
(роли/порты/CRUSH/таблица отказов/ограничения владельцу). Ключевое:

RF3 по трём нодам на 2 нодах **невозможен** — это арифметика, не настройка.
Рабочая конфигурация полигона:

- 2 ноды × 2 NVMe = 4 OSD, по одному OSD на диск;
- CRUSH-правило с `chooseleaf ... type host` → реплики на разных **нодах**
  (у нас это уже есть: failure domain = host, проверено `uniformity_test.go`);
- `replicas=2`, `min_size=1`. Кворум 2/2: запись требует обе ноды; при
  потере одной — том **не пишет** (hard-семантика ставит гостя на паузу,
  это наш же дизайн) и **читает** с оставшейся. `min_size=1` — это не
  «кворум 1 из 2», а разрешение тому существовать в деградации; честная
  формулировка для полигона: **кластер из двух нод переживает потерю ноды
  только на чтение, запись — только с третьей нодой.**
- Вывод, который надо записать в ожидания владельца: **третья нода (любая
  слабая, хоть HDD-бокс) превращает «только чтение» в «пишем в деградации»
  и даёт RF3.** Это самое дешёвое улучшение надёжности полигона.

### M6.2 Мета: главная развилка — **РЕШЕНО: (c) raft, реализовано**

`pkg/meta` — это `DirStore`: каталог JSON-файлов на **локальном** диске с
poll-watch. Интерфейс (`Get/Put(cas)/Delete/List/Watch`) etcd-формы, то есть
заменить можно, не трогая клиентов, — но сейчас два процесса на **разных**
нодах должны видеть один каталог. Варианты:

| Вариант | Что | За | Против |
|---------|-----|----|----------|
| (a) общий каталог по NFS | DirStore поверх shared FS | 0 строк кода | NFS = единая точка отказа; CAS/poll-семантика поверх NFS — «хрупко» в самом мягком смысле; документировать как **lab-only** |
| (b) **мета в демоне** (рекомендация MVP) | `unistord -meta-role active\|passive`: тонкий KV-RPC поверх существующего `sdsnet` + `meta.Store` поверх него; активная нода — единственный писатель | 0 новых зависимостей, один и тот же framing, CAS и watch ложатся на `Put(cas)`/`Watch` напрямую; пассивная нода — read-реплика и hot-standby; работа ≈ 1–2 недели | Failover = ручной/внешний (для 2 нод приемлемо: один активный писатель, второй поднимает meta при смерти первого) |
| (c) встроенный raft-KV (antietcd-подобный) | roadmap-пункт «`pkg/mds` поверх etcd / embedded» | Честный HA на 3 адресах, watch из коробки | Самый дорогой пункт, и на **двух** нодах raft не даёт кворума при отказе одной — то есть для полигона покупает меньше, чем стоит |

**Рекомендация была: (b) для MVP, (c) когда будет 3+ ноды.** Владелец
решил: **сразу (c)** — raft, со свидетель-ногодой без стораджа. Реализовано
в `pkg/meta/raftstore.go` + `pkg/meta/raftproxy.go` (та же
`meta.Store`; кворум-потеря = read-only 503; форвард записей лидеру с
read-your-writes). Консенсус-ядро: сначала hashicorp/raft, затем по
решению владельца перенесено на **etcd-io/raft v3.7.0 как библиотеку**
(вариант (e), §ниже — «используем etcd, но не внешний сервер, а у себя»):
`raft.RawNode` in-process, никакого etcd-сервера в деплое. Для полигона это означает: **честный HA на 3 адресах
(2 рабочие ноды + любая слабая третья как свидетель)**; запись живёт при
потере любой одной из трёх, при двух — только чтение и экспорт.

### M6.2-бейк-офф: «на коленке» raft vs embedded etcd vs antietcd

Владелец спросил: *«ты пытаешься на коленке сделать raft. может просто
использовать etcd пакет?»* и добавил *«есть исходники минирафта в витасторе
(antietcd)»*. Проведён hands-on spike (модуль-копия, `meta.Store` поверх
embedded etcd `go.etcd.io/etcd/server/v3` v3.5.21, три member'а в одном
процессе). **Вывод: raft оставляем; etcd не добавляем.** Замеры ниже.

Реализация `EtcdStore` (получилась — контракт `meta.Store` покрывается
полностью: CAS через `Txn(If ModRevision==casRev)`, rev = `Header.Revision`,
watch через `clientv3.Watch`, ключ `/prefix/key`). Оба spike-теста зелёные:
контракт (CAS-конфликт между нодами, read-your-writes через `WithSerializable`,
list, put/delete-события) и кворум-потеря. Замеренные оси:

| Ось | hashicorp/raft (сейчас) | embedded etcd v3.5.21 | antietcd (vitastor) |
|-----|------------------------|----------------------|---------------------|
| Зависимостей в графе | **135** | **1053** (grpc, zap, prometheus, k8s io, otel…) | 0 Go-зависимостей (C++ sidecar) |
| Размер `unistord` | **13.6 МБ** | **30.5 МБ** (×2.2) | 13.6 МБ + внешний бинарь antietcd |
| Наш «на коленке» код | raftstore.go+raftproxy.go ≈ **943 строк** | ~**230 строк** (clientv3 сам роутит к лидеру — прокси не нужен) | тонкий etcd3-клиент поверх HTTP |
| Чтение при потере кворума | **да** (локальный FSM всегда отвечает) — совпадает с решением №3 | да, **только serializable-чтениями** (линеаризуемые падают); проверено: serializable Get ответил, запись упала в `context deadline exceeded` | да (у vitastor read с локальной реплики) |
| Зрелость консенсуса | hashicorp/raft — боевой, но обвязка наша | **etcd — индустриальный, Jepsen-пройденный** | свой raft vitastor, Jepsen-пройден (3.0.2) |

Как это ложится на наши решения:
- **Зависимости/размер.** 1053 модуля против 135, бинарь ×2.2 — весь etcd-граф
  тянется ради KV на ~десятки ключей полигона. Для «ровно два бинарника» это
  противоречие.
- **Чтение при развале кворума** (решение №3 «рафт развалился — только
  чтение»). Наш raft отвечает из локального FSM по определению. У etcd
  линеаризуемое чтение **умирает** вместе с кворумом; требуемое поведение
  достижимо только `WithSerializable`-чтениями — то есть мы сознательно
  отказываемся от guarantee etcd и получаем ровно то, что у нас уже есть.
- **Antietcd** (ответ на 2-й вопрос): это C++-демон с подмножеством etcd v3
  HTTP/JSON API, **Go-биндингов нет** (репозиторий на self-hosted
  code.vitastor.io, из окружения недоступен; в vitastor он отдельным
  бинарём, не submodule — в `.gitmodules` только cpp-btree/json11). Вариант
  переиспользования — запускать antietcd sidecar'ом + писать свой etcd3-клиент
  поверх его HTTP-подмножества. Это больше работы и новый внешний процесс,
  чем наш встроенный raft, ради консенсуса, который мы и так берём из
  библиотеки. Vitastor ушёл с внешнего etcd именно из-за веса зависимостей и
  нагрузки (их заметки) — для Go-демона embedded etcd повторяет обе цены.

**Решение: остаёмся на hashicorp/raft (M6.2 реализован).** Embedded etcd
остаётся задокументированным fallback'ом на случай, если экосистемно-доказанный
консенсус станет важнее свойства «читаем при partition» и веса зависимостей;
antietcd — опция (d) только если решим конвергировать с vitastor-стеком.
Spike-код (`etcdstore.go`, trio-тест) сохранён в session files
(`files/etcd-spike/`), в основное дерево не добавлялся.

**etcd-io/raft подробно** (единственный осмысленный «меньший»): ядро
отделено из etcd v3.7, зависит только от protobuf (+testify/datadriven в
тестах) — 14 модулей против 95. Реальное окно экономии в нашем демоне:
граф 135 → ~54, бинарь 13.6 → ~12.7 МБ (−0.9 МБ). Цена: это **не**
библиотека «под ключ» — Ready-цикл (`Ready{HardState,Entries,Snapshot}` →
свой персист → `Advance`) означает написать заново: транспорт поверх
нашего sdsnet-фрейминга (~200 строк), WAL-лог на bbolt (~250 строк,
bbolt уже в зависимостях), снапшот-мост к нашему FSM (~100 строк),
Ready-цикл с ReadIndex (~150 строк). Итого **+400–600 строк нашей
обвязки** вместо встроенных hashicorp-механизмов, плюс переписывание
наших зелёных raft-тестов на новый цикл. Наш read-your-writes (ожидаем
appliedIdx) ложится на Ready-цикл естественно, семантика «кворум лёг —
читаем из локального FSM» сохраняется.

**Решение было: не мигрируем.** Экономия (−81 модуль графа, −0.9 МБ бинаря)
покупается ценой в 400–600 строк критичного кода (транспорт+лог), который
сейчас написан, протестирован и поддерживается hashicorp. etcd-io/raft
зафиксирован как **опция (e)**: мигрируем, если (1) бюджет зависимостей
ужесточится законодательно/секьюрити-политикой, или (2) hashicorp/raft
перестанет поддерживаться — тогда это прямой преемник с индустриальным
консенсусом без etcd-сервера.

> **ОБНОВЛЕНИЕ — вариант (e) РЕАЛИЗОВАН (решение владельца: «используем
> etcd, но не через внешний сервер, а делаем у себя»).** `pkg/meta`
> перенесён с hashicorp/raft на `go.etcd.io/raft/v3 v3.7.0` — это то же
> ядро, что крутится внутри etcd (Jepsen-линияж), но **как библиотека в
> нашем процессе**: `raft.RawNode` + Ready-цикл, наш транспорт
> (`rafttransport.go`, sdsnet-фрейминг), лог и hardstate в bbolt рядом с
> FSM, снапшоты через `ApplySnapshot/CreateSnapshot`, членство через
> ConfChangeV2 (адрес пионера едет в `Context`). Оценённые 400–600 строк
> обвязки написаны; hashicorp/raft и raft-boltdb удалены из `go.mod`
> (`go mod tidy`). Всё ядро зависимостей raft — 14 модулей etcd-raft +
> protobuf + bbolt (bbolt у нас и был). Тесты: весь raft-набор
> (`TestRaftStore*`: CAS на 3 узлах in-memory, read-only при потере
> кворума, watch на фолловере, close/reopen с восстановлением hardstate,
> конкурентный CAS, forwarded write + read-your-writes по реальному TCP)
> зелёные с `-race`; живой e2e-трио (2 OSD-ноды + свидетель): импорт
> 8 МБ octet-stream через фолловера (прокси к лидеру), экспорт побайтово
> совпадает, создание тома через свидетеля (чистый прокси), kill 2/3 →
> выживший отдаёт чтение и экспорт, запись 503 `is_read_only`, ре-джой →
> лидер выбирается, запись возобновляется, meta реплицируется на всех за
> ~2 с. Прямая выгода владельцу: детерминированный Ready-цикл с
> детерминированным выбором лидера (детский timer у etcd-raft), минус
> 81 модуль графа, минус внешняя обвязка hashicorp.

**braft (вопрос владельца, по мотивам витасторовских заметок).** braft —
**C++**-библиотека Baidu поверх brpc (4.2k★), индустриальная внутри Baidu,
но: последний релиз **v1.1.2 — апрель 2021**, последний коммит — октябрь
2024 (спячка ~2 года; жив у только brpc-родитель). **Go-биндингов нет**
(в Go-экосистеме braft не оборачивается никем). Для vitastor он привлекателен
именно потому, что vitastor — C++: у них braft встраивается нативно. Для
нашего Go-демона путь один — **cgo-обёртка или sidecar-процесс с IPC**, то
есть ровно та же категория, что antietcd: второй язык сборки, второй
процесс, кросс-языковый RPC в критичном пути консенсуса — и при этом
апстрим спящий. Сравнивать его с «меньшими Go-либами» некорректно: по
весу интеграции он проигрывает и embedded etcd (у того хоть Go-нативный
API из коробки). Записан как вариант (f) рядом с antietcd — интересен
только при полном конвергенции с vitastor-стеком (там braft нативен).

Отдельно openraft (Rust, тот же класс «упоминается в raft-обзорах»):
живой и активный (0.10.0-alpha, обновлён 11.2026), но (1) Rust → FFI/сайдкар
для Go, (2) стабильной 1.0 нет — не кандидат по той же причине, что braft:
кросс-языковая интеграция консенсуса дороже самой миграции.

**Вариант (g): «написать свой мини-raft» (путь vitastor/antietcd).**
Владелец уточнил: речь про свой raft, как antietcd у vitastor. Оцифровано,
с чем сравнивать:

- **Что такое «мини-raft» по объёму.** Ядро etcd-raft (эталонный «мини»):
  raft.go 2162 + log.go 576 + rawnode.go 557 + node.go 616 + storage.go 326
  + confchange 1000 + quorum 876 + tracker 1247 ≈ **7.8k строк** чистого
  стейт-машины + **4.3k строк только юнит-тестов ядра** (raft_test.go) +
  многолетний Jepsen. Учебные версии (eliben/raft ~2k строк) не имеют
  pre-vote, joint-consensus, снапшотов, линейлизуемого чтения — то есть
  это не прод.
- **Что взял vitastor своим путём.** antietcd — их собственный C++ raft
  (коды на code.vitastor.io, недоступны); цена пути видна по их же
  репозиторию: отдельный бинарь-кворум + chaos-тесты (kv_stress 707
  строк, chaos-тесты PG 188k строк, chaos KV добавлен только в 3.2.3 —
  2026 год, то есть тестирование консенсуса у них продолжается годами).
  Их мотивы: (1) в 2019 в C++ не было etcd-raft-аналога, (2) жёсткая
  интеграция в свой epoll/ringloop-цикл без потоков и аллокатора — у vitastor
  это реальные требования архитектуры.
- **Наши требования таких мотивов не дают.** У нас Go с горутинами,
  события — обычный net-транспорт; интеграция «внутрь своего цикла» не
  даёт ничего, чего не даёт Ready-цикл etcd-raft. Наш текущий «на коленке»
  код (raftstore+raftproxy, 943 строк) — это обвязка над библиотекой, не
  raft; raft-ядро — отдельный класс сложности (баги: split-brain, потеря
  коммитов, тихая порча метаданных под partition — всплывают через годы).
- **Реальная экономика.** Свой raft: −95 зависимостей, −0.9 МБ, полный
  контроль. Цена: 3–5k строк ядра + 3–5k строк тестов + хаос-тесты
  (реестр: partition/pause/dupe-replication/lossy-log/snapshot, как у
  etcd-raft в tests) — это квартал работы с нулём маржи на ошибку, и
  ответственность за консистентность метаданных полигона целиком наша.

**Вердикт (g): не пишем.** «Мини-raft» в Go уже существует и бесплатен —
это вариант (e) etcd-io/raft: то самое ядро, что antietcd по зрелости
(общий линияж с etcd, Jepsen), 14 модулей, без чужих транспорта/лога.
Писать своё ядро имеет смысл только при эмбарго на 14 модулей/protobuf
(air-gap аудит) либо как образовательная задача. Если «минимализм
зависимостей» станет жёстким требованием — идём в (e), не в (g).

### M6.3 Recovery — ✅ реализовано (v1)

Клиент умел: не терять подтверждённые записи, работать с мёртвым OSD,
эвиктить по `out_time`, восстанавливать вес по проберу. Реализовано то,
чего не хватало — «найти расхождения и залить с живой реплики»:

- `Volume.RecoveryCheck` / `Cluster.RecoveryScan` (`pkg/client/recovery.go`):
  по всем объектам тома (`NumObjects`) считает CRUSH-таргеты и сравнивает
  с реальностью каждого OSD; расхождение = объект есть на части реплик
  (diverged) или отсутствует (missing, чинится с любой живой реплики);
  тонкие «дырки» за пределами записи не считаются; мёртвый OSD помечается
  в `Down` и не порождает задач (бессмысленно лить на дохлый диск);
- `Volume.Recover`: копирует объект с живой реплики на недостающий target,
  темп ограничен `qos.Pair` только по линии записи — по умолчанию
  200 iops / 200 MiB/s, починка не обижает живых гостей. `RecoveryStats`
  (Copied/Bytes/Failed/Skipped) — построчно в лог;
- триггеры: `unistorctl recovery ls | check <vol> | run <vol>
  [-iops N] [-bps B]`, HTTP `GET /v1/recovery` (скан),
  `GET/POST /v1/recovery/{name}` (проверка/починка, темп query-параметрами);
- проверки на живом 3-OSD кластере (`admin_vacuum_recovery_test.go`):
  «саботаж» = рестарт OSD + удаление его объектов на диске → скан даёт
  `to_repair`, починка восстанавливает реплики, повторная проверка чиста.

Поток-оптимизации (batch-копирование, приоритетные очереди, recovery по
PG) — отложены: на 2 нодах полигона placement от CRUSH детерминирован,
расхождения редки и чинятся поштучно. **3–5 дней уложились.**

### M6.4 Health и runbook полигона — ✅ реализовано (кроме `/metrics`)

- `/v1/status` — машиночитаемо: ✅ OSD up/down (свежий пинг каждого OSD,
  `Cluster.ProbeOSDs`), вес и эвикция (`weight<=0` после `out_time`),
  epoch карты, здоровье томов (`Cluster.VolumeHealth`: живые targets vs
  `min_size`, «degraded» = живых меньше quorum — у нас деградация на

  место по OSD (локальные OSD процесса: `store.Usage` + statfs
  free/total через `diskRegistry`; удалённые OSD — только liveness),

  закрывает алерты «OSD down», «свободно <10%», «том деградировал»,
  «raft без лидера»;
  `unistorctl status -http URL` — человекочитаемый вывод того же JSON;
- `/metrics` — **отложено**: JSON-опрос покрывает полигон, Prometheus

## 10. Открытые решения (нужно решение владельца)

1. **Мета на 2 нодах** (§8.2): **РЕШЕНО — (c) встроенный raft, реализовано**
   (hashicorp/raft, свидетель-нода без стораджа, read-only при потере
   кворума, форвард записей лидеру). Неделя 4 разблокирована.
   Бейк-офф «embedded etcd vs наш raft» проведён и закрыт в пользу raft
   (§8.2 M6.2-бейк-офф): etcd — ×7.8 зависимостей, ×2.2 бинарь, а чтение
   при partition всё равно требует serializable-обхода, то есть решения №3
   он не улучшает. Antietcd — вариант (d) только при конвергенции с
   vitastor-стеком. «Меньшие либы» тоже сравнены (часть 2 того же
   бейк-оффа): hashicorp/raft и так лёгкий (95 модулей), единственная
   живая меньше — etcd-io/raft (ядро etcd, 14 модулей, но без транспорта
   и лога) — опция (e), миграция не окупается. braft/openraft (не-Go) —
   вариант (f) рядом с antietcd: cgo/сайдкар ради консенсуса, апстрим
   braft спит с 2021 (релиз). «Свой мини-raft» — вариант (g): ядро
   7.8k строк (столько весит etcd-raft) + Jepsen-тесты годами; в Go
   «мини-raft» уже готов и бесплатен — это (e), своё ядро пишем только
   при эмбарго на 14 модулей.
2. **Экспорт в гостя для враждебных ВМ**: VDUSE в хосте (рекомендую по
   безопасности и по скорости, и он уже написан) vs NBD-клиент в госте
   (проще деплой). Связано с roadmap «Риски» п.2 и п.7.
3. **Третья нода**: просить железо под RF3 (даёт запись в деградации) или
   живём с «при смерти ноды — только чтение»? Это вопрос к железу, ответ
   сильно меняет ожидания полигона.
4. **Источник blob'а при импорте**: только upload (`PUT body`) или также
   pull по URL (`--url`, удобно для CI-артефактов). Рекомендую оба, оба дешёвые.
5. **Снапшоты: нужны ли клоны** (партии одинаковых ВМ) — ответ «нужны»,
   и они сделаны: копия меты поверх расшаренной цепочки + `genrefs`
   (вторая половина M3 закрыта, см. §5).
6. **Аутентификация data path (`sdsnet`)** сейчас vs после закрытия сети.
   Рекомендую: сеть закрываем сразу (дешевле), токен в handshake — вторым
   эшелоном.

## 11. Что НЕ делаем (для этого полигона)

- Erasure coding — на 4 дисках бессмысленно (RS требует ≥6–8 целей).
- RDMA, vhost-user/vfio-user, NVMe-эмуляция в госте — экспорт NBD/VDUSE
  закрывает требование; остальное по roadmap Фазы 4/5.
- qemu-img-конвертеры, qcow2/VHDX — потребитель конвертирует сам.
- Мульти-кластерность, репликация между площадками, key-management (KMS).
- Дашборды/визуализация — достаточно `/v1/status` + Prometheus.
- Изоляция на уровне OSD-процессов: один `unistord` на ноду со всеми OSD —
  осознанно (изоляция томов обеспечивается OID-бейзами и квотой, не
  процессами).
