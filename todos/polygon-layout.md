# Layout полигона: 2 ноды × 2 NVMe (+ третья нода-свидетель)

Цель: выдать тестовым ВМ (гарантий на которые нет) блочные диски на
реальном железе полигона и честно зафиксировать, что это железо может и
чего не может. Операции — в `runbook.md`; это документ про конфигурацию
и ограничения (план M6.1).

## Железо и роли

| Роль | Нода | Диски | Что крутим |
|------|------|-------|-----------|
| storage A | 10.0.0.1 | NVMe1, NVMe2 | unistord: OSD 0 (nvme1), OSD 1 (nvme2), raft voter, admin :8443, NBD/VDUSE экспорты |
| storage B | 10.0.0.2 | NVMe3, NVMe4 | unistord: OSD 2 (nvme3), OSD 3 (nvme4), raft voter, admin :8443, экспорты |
| witness C | 10.0.0.3 (любая слабая, хоть HDD-бокс) | не нужны | unistord `-raft` без `-osd`/`-export`: голосующий свидетель meta |

По одному OSD на NVMe: `id@/mnt/disk/osdN@addr:port`, данные — объекты в
`-store`-каталоге на этом диске. QoS «потолок диска» ставится per-OSD
агрегатом `-osd-qos` (общий лимит всех томов на диске), «потолок юзера» —
классом `-qos` на томе; админский трафик (import/export) не ограничен.

## Сети (порт-план)

| Порт | Плоскость | Кто слушает |
|------|-----------|-------------|
| 7000+ | данные (sdsnet) | каждый OSD |
| 9401+ | raft meta | raft voter'ы (A, B, C) |
| 9501+ | raft-proxy (форвард записей follower → leader) | все три |
| 8443 | admin HTTP (`/v1/status`, import/export) | storage-ноды |
| 10809 | NBD (гости) | storage-ноды |

Данные и meta — разные плоскости; raft-proxy обязателен, иначе запись,
попавшая на follower, получит 503 вместо форварда лидеру.

## Размещение данных (CRUSH)

- Failure domain = **host**: правило `chooseleaf firstn 0 type host`
  кладёт реплики объекта на разные ноды (не на разные диски одной ноды —
  это проверял `uniformity_test.go` в pkg/placement).
- `replicas=2`, `min_size=1`, `pg_num=64` на том.
- 4 OSD на 2 host ⇒ каждый объект лежит ровно по одной реплике на
  каждой ноде: **смерть ноды не теряет данные, смерть диска тоже**
  (вторая нода держит полную копию).
- RF3 по трём host на двух нодах невозможен арифметически — не настройка.

## Честная таблица отказоустойчивости

Событие → что видит гость (свидетель C жив, 2 storage-ноды):

| Событие | Запись | Чтение | Данные |
|---------|--------|--------|--------|
| диск умер (1 из 4 OSD) | идёт (реплика на второй ноде; мин_size=1 покрывает 1 мёртвый target из 2) | идёт | целы, нужна recovery-починка (M6.3) |
| нода умерла (2 из 4 OSD) | **идёт** на оставшуюся реплику (мин_size=1), гость может встать на паузу на время детекта | идёт | целы на живой ноде |
| meta-кворум потерян (умерли 2 из 3 voter) | 503 / пауза гостя | **только чтение + export** | целы |
| обе storage-ноды умерли | — | — | целы, ждём возвращения; экспорт с живой meta |

Без свидетеля (2 voter): потеря любой ноды = meta read-only, то есть
данные на второй ноде читаются и отдают экспортом, но контроль (создать/
удалить/QoS) заморожен до возвращения кворума. Формулировка для
владельца: **третья (любая слабая) нода превращает «только чтение» в
«пишем в деградации» — самое дешёвое улучшение полигона.**

`min_size=1` — не «кворум 1 из 2 по умолчанию», а разрешение тому
существовать в деградации; запись при двух живых нодах идёт на обе
реплики (кворум 2/2 как полный путь).

## Поведение при отказе (механика)

1. Сбой запроса к OSD → клиент копит отказы; `osd_out_time` (по
   умолчанию 600 с, `Cluster.SetOutTime`) — dwell, в течение которого
   OSD сохраняет вес.
2. Dwell истёк → эвикция: вес → 0 в meta, новая epoch placement, у
   томов пересчёт live targets; `status` показывает `evicted` + warning.
3. OSD вернулся на свой data-dir → сам регистрируется, после пробера
   вес восстанавливается (клиентский probe). Расхождение объектов чинит
   recovery (M6.3, в плане): до него — сверка/докачка из бекапа.
4. Рафт: потеря кворума = read-only мета (данные читаются, админ пишет
   503 с подсказкой лидера); возврат voter'а возвращает запись.

## Ограничения, которые надо назвать владельцу до старта тестов

1. Recovery (M6.3) нет: после долгого отсутствия ноды/диска реплики
   расходятся — чинится бекапом, не кластером.
2. Снапшотов (M3) нет: «клон ВМ» = импорт того же образа в новый том.
3. RF2 без свидетеля = контроль read-only при смерти ноды; со
   свидетелем — пишем, но деградированный том (1 реплика) переживает
   вторую смерть только на чтение.
4. Тонкие тома (quota) при исчерпании полигона: гость получает ENOSPC —
   это ожидаемое поведение, не авария; мониторинг `status` (<10% free).
5. Гость с гарантиями «никакими» не должен иметь доступа к admin HTTP
   и порту raft — только NBD/VDUSE.
