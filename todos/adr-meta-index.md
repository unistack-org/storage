# ADR: in-memory мета-индекс объектов (Фаза 5) — один объект = одна запись меты

Дата: 2026-11-10. Статус: принят. Реализация: `pkg/store/meta.go` (тип и
инвариант), `pkg/store/store.go` (`Load`, `openSlow`, `Stat`, `StatInfo`,
`ObjectState`, `removeFile`, счётчики), `pkg/store/journal.go` (оверлейные
Stat-семантика и applier), метрики: `store.MetaInfo` → `Daemon.MetaInfo` →
`/v1/status` (`meta_objects`/`meta_ram`) → gauge `unistor_osd_meta`.
Тесты: `stats_test.go` (`TestMetaIndexCounters`), `stat_overlay_test.go`,
`statinfo_test.go` (`TestStatInfoTracksAllocation` — регресс alloc-hint).

## Решение

Мета-индекс объектов живёт в RAM процесса OSD и является **единственным
источником истины на пути запроса** после запуска. OSD не выполняет
`os.Stat`/чтение заголовка объекта с диска при обслуживании запроса:

1. **Одна запись на объект.** `objMeta{size, alloc, allocKnown}` —
   24 байта на объект (`pkg/store/meta.go`). Индекс `map[object.OID]objMeta`
   под тем же `Store.mu`, которым уже сериализуется вся мутация набора
   объектов. Инвариант: **все метаданные одного объекта — в одной записи**;
   никаких вторичных структур, которые могут с ней разойтись.
2. **Пополнение.** `Load()` при старте (`store.New` вызывает его сам):
   один `ReadDir`, размер берётся из dirent — **ноль per-file `stat`
   syscall'ов**. `allocKnown=false` у индексированных без открытия
   объектов: `alloc` — только *подсказка*, её источник — `st_blocks`
   открытого файла (см. «Грабли»).
3. **Обновление.** `openSlow` пишет запись при создании/открытии (там же
   бесплатный `alloc` из handle-Stat, вне пути запроса); запись, рост и
   flatten обновляют `size` под `s.mu`; punch сбрасывает `allocKnown`
   (следующий `StatInfo` перемерит — это фоновый путь вакуума, не
   путь запроса); `removeFile` удаляет запись.
4. **Запросы.** `open` (чтение) и `Stat`/`StatInfo` отвечают из индекса;
   `os.Stat` на пути запроса не осталось.

## Цена: ~18 МБ на ТБ, а не 512

Числа Vitastor из доклада Highload'2025, которые мы обязаны были
сравнить: **663 / 371 / 152 МБ RAM на ТБ** (сырьё+btree+журнал / +11 % /
+18 % худший случай) — это индекс **на 4 KiB-блок** (их единица
данных = единица меты). Наш индекс — **на объект** (4 МиБ), потому что
у нас нет block-уровневой меты в OSD: объект цельный, его координаты
лежат в бите тома, а не в OSD. 72 Б на объект (24 Б значения + ~48 Б
накладных расходов Go-карты) ⇒ 72 Б / 4 МиБ ≈ **18 МБ на ТБ** — на три
порядка дешевле их цифры при том же свойстве «мета всегда в RAM».
Плотность записей одного объекта в один блок меты (их инвариант из
доклада: потеря блока меты = «выбросить весь диск») у нас тривиально
выполнен: блок меты = объект, а сам индекс восстанавливаем с диска за
один `ReadDir` (нет durable-меты ⇒ нет и окна потери).

## Log-structured мета — сознательно НЕ берём

Им log-structured нужна, потому что их мета durable (btree + журнал
меты на SSD, отсюда +11/+18 % и «block of meta»). Наша мета — кэш
поверх POSIX-файлов: пережитый процесс перечитывает каталог и
восстанавливает индекс; файл сам является durable-метой размера/существования.
Добавлять durable-мету = добавить второй источник истины и окно
рассогласования с ФС — ровно та грабля, из которой они строили журнал
меты. Если понадобится durable-мета на объект (версии, чексуммы
блоков), это отдельный ADR поверх этого инварианта.

## Семантика в journal-режиме (оверлей)

Журнал даёт окно между «запись подтверждена» и «файл объекта догнал
лог». Правила (`Stat`/`StatInfo`/`ObjectState`):

- Снимок оверлея берётся **до** снимка индекса: запись покидает оверлей
  только после того, как applier обновил индекс, — снять оверлей первым
  значит максимум недооценить pop (а недооценка конца оверлея
  безопасна: размер файла не меньше).
- `Stat`/`StatInfo` для **существующего** объекта: `size = max(индекс,
  конец оверлея)`; `alloc = max(alloc, конец оверлея)` — байты
  подтверждённой записи логически принадлежат объекту, даже когда файл
  на отложенной аллокации (APFS/XFS) отстаёт; такой замер **не
  кэшируется** в индекс (это не устойчивое состояние файла).
- **Новый** объект с только оверлейными записями: файла нет —
  `Stat`/`StatInfo` честно отвечают not-exist (контракт уровня файла:
  эти API используются вакуумом и `unistorctl`, которым нужен диск),
  а `ObjectState` отвечает `present=false, pending=true` — это API
  NBD base:allocation, и гость по нему видит «данные есть» до
  появления файла. Чтение шьёт байты из оверлея (read-your-writes,
  `journal_test.go`).
- **Инвариант аллокации для вакуума:** `alloc=0` у объекта с данными
  больше не встречается (регресс, который чинил `TestStatInfoTracksAllocation`:
  journal-путь не обновлял alloc-hint ⇒ вакуум хотел выбросить «пустые»
  объекты).

## Грабли и решения

- **alloc как подсказка.** `st_blocks` известно только для файлов,
  открытых этим процессом; индексированный на `Load` объект имеет
  `allocKnown=false` ⇒ `StatInfo` делает один `os.Stat` (фон/вакуум) и
  при ненулевом результате чинит подсказку. Punch тоже сбрасывает её.
  Это цена «индекс без durable-меты»: аллокацию нельзя вывести из
  dirent.
- **Load идемпотентен на объект** (пропускает уже индексированные и
  открытые), поэтому `New` + явный `Load` вызывающего безопасны;
  явные вызовы убраны из `sds-nbd/nbd/store_backend.go`.
- **Usage** остаётся суммой логических размеров; индекс — тот же учёт,
  `meta` и `files` обновляются под одним `s.mu` (одна запись = одна
  точка истины и для учёта).
- **Наблюдаемость:** `MetaInfo() (objects, ram)` — количество и расчётная
  цена RAM; в `/v1/status` (`meta_objects`/`meta_ram`) и gauge
  `unistor_osd_meta{osd,name}`; только через существующий экспорт
  Prometheus-текста, который собирает VictoriaMetrics (политика метрик
  `todos/runbook.md` — второй стеки метрик нет).

## Тесты

- `TestMetaIndexCounters` — популяция индекса, RAM-оценка, удаление
  уменьшает индекс после перезагрузки;
- `TestStatInfoTracksAllocation` — alloc>0 у записанного объекта в обоих
  режимах (регресс journal alloc=0);
- `TestStatJournalOverlay` — заморозка applier'а (`pauseApplier`):
  pending-объект, max-семантика Stat/StatInfo через оверлей, Sync/Remove
  как чекпоинты, обходящие заморозку.
