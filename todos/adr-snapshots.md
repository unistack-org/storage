# ADR: снапшоты томов (M3) — поколения без переименования

Дата: 2026-02-05. Статус: принят. Реализация: `pkg/meta/snapshots.go`,
`pkg/client/snapshots.go`, `unistorctl vol snap`, admin `/v1/volumes/{n}/snapshot*`.

## Решение

Снапшот = **заморозка текущего поколения и переход на новый частный
диапазон OID** (forward/redo из roadmap, фаза 6), БЕЗ переименования
объектов на OSD:

1. `spec.Snapshot(gen)` — одним CAS-писком меты:
   - текущий диапазон (`OIDBase/Extents`), размер, QoS и **битмап
    аллокации** уезжают в `Snapshots` (запись `GenRecord`, отсортирована
    по возрастанию gen);
   - том получает **новый** зарезервированный диапазон из общего
     аллокатора, `Gen++`.
2. Запись идёт только в live-поколение. Чтение live-поколения: бит live
   битмапа выставлен — читаем live-объект; бит сброшен — идём по
   `Snapshots` от новых к старым, где битмап поколения говорит, где что
   лежит (объект с битом 0 в каждом поколении = логические нули).
3. Откат (`rollback gen`) = CAS: адресация/размер/битмап замороженного
   поколения становятся live; всё, что новее, — мусор, уходит в тумбстон
   вакуума (диапазоны частные, vacuum выметает их целиком).
4. Удаление одного снапшота = CAS: выкинуть `GenRecord` из списка +
   тумбстон на его диапазон. Параллельные удаления сериализуются CAS'ом
   спека — цепочка не рвётся (грабли из плана учтены).

## Почему не rename (как у Vitastor)

- В нашем протоколе нет OpRename; rename = read+write+remove каждого
  объекта = O(ёмкость) трафика на снапшот. Резерв диапазона = одна
  арифметическая CAS-запись меты, данные не трогаются **вообще**.
- Power-loss между rename и метой — реальное окно неатомарности (грабель
  №4 из плана). Здесь мета — единственный источник истины, и она
  пишется атомарно (одна CAS). Прерванный снапшот = утёкший диапазон
  (безвредно, аллокатор монотонный) — идемпотентно повторить.
- Грабель №1 (gen в 8 битах): gen — `uint32`, арифметика 64-битная; тест
  с 300 поколениями.

## Грабли и решения

- **TRIM/DISCARD поверх снапшота.** Дырка в live-поколении не отличима
  от «не аллоцировано», а «не аллоцировано» по цепочке достаёт данные
  снапшота — удалённое «воскресает». Решение: том **с снапшотами** на
  sparse-trim всего объекта материализует нули (обычная запись + зарядка
  квоты); без снапшотов —hole-punch как раньше (нулевая цена функции,
  пока она не включена). Записанный (существовавший) объект hole-punch
  безопасен: объект существует — цепочка не привлекается.
- **Глубина цепочки.** Чтение холодного объекта = 1 RTT на поколение.
  Лимит `MaxSnapshots = 64`; дальше `CreateSnapshot` отказывает.
- **Quota.** Заряжается live-битмап, который теперь **кумулятивный** по
  цепочке: бит i = «блок i читается где-то в цепочке» (снапшот копирует
  битмап предшественника и не сбрасывает его; новая запись в свежий
  диапазон ставит биты как обычно). Это инвариант `Usage()`/снапшотов для
  томов с любой квотой. Поколения снапшотов едят место на OSD сверх
  live-битмапа (старые копии блоков) — видно в `vol snap ls`/вакууме;
  в v1 так.
- **Resize тома с снапшотами** — отказ (v1): сначала rollback. Причина:
  extents живут в поколениях, разрастание «поверх» цепочки усложняет
  Lookup без пользы для полигона.
- **Удаление тома с снапшотами** — тумбстон должен нести ВСЕ диапазоны
  (live + все поколения). Реализовано.

## Границы v1 (сознательно)

- Клоны реализованы (M3, `pkg/meta/clones.go`): клон = копия меты поверх
  расшаренной цепочки источника; ссылки считаются записями под префиксом
  `genrefs:` (ключ — base диапазона). Протокол: клон НАРАЩИВАЕТ ссылки
  до своего CAS, удаление — СБРАСЫВАЕТ после своего CAS; все
  переплетения таким образом ведут к утечкам (лишние записи/объекты),
  но никогда к уничтожению расшаренных диапазонов. Refcount-графа
  общего назначения нет — только счётчики на диапазоны поколений.
- Нет инкрементальных бекапов (M4 = сравнение пар GenRecord по битмапам).
- Снапшот не имеет имени — id это номер поколения (монотонный, uint32).
